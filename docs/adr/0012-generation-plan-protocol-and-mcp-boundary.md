# ADR 0012: 生成计划协议、素材库与 MCP 边界

> Status: Active
>
> 日期：2026-11-03
>
> 决策：Viewer 新增 `viewer.plan/1` 生成计划协议；参考图以内容寻址方式存放在
> `.viewer/refs/`；Agent 通过 **stdio 子进程** 形式的 MCP 服务写入与读取，
> 不开放监听端口、不常驻、不接收外部连接。
>
> 关联设计：[生成计划与节点图设计](../superpowers/specs/2026-11-02-viewer-generation-plan-graph-design.md)

## 背景

Viewer 0.3.0 的评审闭环已经完成：用户在图片上打标记，Agent 通过
`viewer-review-reader` 读取 current。缺的是评审**之前**的一段——用户要生成什么。

批量生成的要求来自对话，天然会漂移：用户今天按套系说，明天按场景说，同一个参考图
被反复贴进聊天。软件需要在本地把这些要求固化成一份可审阅、可追溯、可机器消费的计划。

## 决策

### 1. 计划是两层，不是一棵树

第一层是需求（组、声明数量、意图），第二层是素材（拼装提示词、参考图、规格、模型）。
分开的理由是注意力：没有人能审 500 条生成请求，但所有人都能读 10 个组和几个数字。

### 2. 数量必须被声明并被核对

`declaredCount` 是 Agent 对用户口述数量的声明；实际分镜数由程序统计。两者不一致时
产生 `count_mismatch` **警告**（不是错误）。这是唯一能抓住"用户说 7 张、Agent 写了 6 条"
的位置，所以数量不能只靠数出来。

### 3. 参考图按内容寻址

参考图存放在 `.viewer/refs/<sha256>.<ext>`，计划里只写 `assetId`。
同一份字节永远只有一个文件，去重是结构结果而不是约定；改动一张参考图等于导入一张新的，
旧计划仍可复现。

之所以放在 `.viewer/` 而不是项目根的 `refs/`：参考资料是"打包进工程文件的资源"
（类似 .blend 内嵌贴图），不是用户的产出素材；放外面会混进"全部素材"与搜索。

### 4. MCP 是 stdio 子进程，不是本地服务

`viewer-plan-mcp` 与已有的 `viewer-review-reader` 同构：一次性进程、JSON-RPC over stdio、
由 Agent 自己拉起、用完即退。App 不感知它，界面照旧靠文件监听刷新。

**不做的**：不监听端口、不做 HTTP/SSE、不常驻、不接受项目外的写入、不执行任何生成命令。

这条边界保证"应用不访问网络"的承诺不被改变。若未来需要长连接，必须另立 ADR 并重新评估
安全模型。

### 5. 版本跟随需求，尝试不升版本

`revision` 只随需求变化（组、数量、意图、取值、分镜内容）。换模型重试不升版本，
记在 `.viewer/plans/runs/` 的 run 记录里，并带 `shotHash` 供外部工具跳过未变的分镜。

## 影响

- `viewer-domain` 新增 `plan` 模块；`viewer-application` 新增唯一的校验与拼装实现；
  `viewer-infrastructure` 新增素材库、仓库、读取器与 MCP 两个二进制。
- 产品边界文档需改写：原 `PRODUCT_SPEC` §9 写的是"不提供 MCP"，现改为
  "提供只读/写入型 stdio MCP，不提供监听服务"。
- 不新增外部依赖：`sha2`、`serde_json` 均为工作区既有依赖。
- 计划协议与评审协议彼此独立，互不影响；删除 `.viewer/plans` 后回到"无计划"空态。

## 备选方案与放弃原因

| 方案 | 放弃原因 |
| --- | --- |
| 复用评审协议（给 `FeedbackAnchor` 加 plan node） | 评审 target 强制 `asset_version_id`、证据是 PNG、归档语义是"上一轮图片意见"，计划节点没有这些 |
| 本地 HTTP 服务 + REST | 打开常驻监听面，与"无网络访问"的产品承诺冲突 |
| Agent 直接手写 JSON 文件，不加校验 | 半截文件、未知字段、缺失素材会静默进入项目，用户只能靠肉眼发现 |
| 参考图存路径而非内容哈希 | 改名/移动即断链，且无法去重 |
