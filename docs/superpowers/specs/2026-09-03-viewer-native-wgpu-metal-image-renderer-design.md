# Viewer 原生 wgpu／Metal 图片渲染架构设计

> Status: Approved
>
> 日期：2026-09-03
>
> 类型：图片预览与图片评审渲染子系统架构重构
>
> 约束：不新增产品功能，不改变任何用户可见行为

## 1. 背景与根因

Viewer 当前使用 Tauri 2 的 macOS WKWebView 承载 React 界面，图片预览由 HTML 图片、
CSS 变换、DOM 覆盖层和高分辨率 Canvas 共同完成。WebKit 会间接使用 GPU 合成，但 Viewer
没有专门拥有图片纹理、帧调度、资源预算或渲染线程。当前热路径存在以下结构性问题：

- 平移手势的每次指针移动都会进入 React 状态更新；
- 预览投影在 React 渲染期间读取 DOM 几何；
- 视口投影变化会触发标注 Canvas 重设缓冲区并重绘完整场景；
- 放大镜、图片和评审标记由不同渲染路径解释同一组坐标；
- 原图预览会过早请求完整原图派生结果，解码、传输和显示粒度没有统一资源调度；
- 图片交互、评审保存和页面状态之间仍存在不必要的相互等待或全量刷新风险。

以 6570 × 4380 的 8 位 RGBA 图片为例，仅一份未压缩像素约占 110 MiB。如果同时存在解码缓冲、
浏览器图片、高分辨率 Canvas、放大镜副本和中间结果，统一内存压力会快速放大。继续在 DOM 热路径
上做局部优化无法建立稳定的 60／120 Hz 帧预算，也无法形成未来 Windows 后端可复用的渲染边界。

本设计采用 React／Tauri 产品外壳与原生 wgpu／Metal 图片视口组合的混合架构。macOS 原生视口
负责逐帧交互和 GPU 绘制，React 继续负责工具栏、意见栏、历史、文本输入和页面导航。评审领域状态
与 Agent 读取协议保持不变。

## 2. 已确认的架构决策

1. 采用原生 wgpu／Metal 混合架构，不把 WKWebView WebGPU 作为 macOS 13+ 的基础实现。
2. 分阶段迁移：旧渲染器和新渲染器先隐藏在统一 RendererPort 后共存，通过门禁后删除旧热路径。
3. 稳定后只保留新引擎，不增加轻量 CPU 预览兜底，也不永久维护两套完整渲染算法。
4. 当前只实现 macOS Metal 后端；核心场景、坐标、资源和命令协议保持平台无关，为未来 Windows
   DX12 后端保留边界，但本轮不实现 Windows。
5. 第一批生产迁移只覆盖单图预览和图片评审热路径：适窗、缩放、平移、旋转、全部标记、命中检测、
   放大镜和图片切换。
6. 网格缩略图、对比预览和视频播放暂时保留现有实现。未来对比预览复用多个原生图片视口；视频仅预留
   统一场景／标注接口，不改变当前 libmpv 路径。
7. 原生视口拥有高频输入和逐帧状态，React／Tauri 之间只交换低频语义命令和事件。
8. 默认图片显示尺寸只由应用方向后的图片长宽比和可用预览区域决定，与图片像素总量、文件体积和
   图片内容无关。像素数量只参与清晰度层级和资源预算计算。

## 3. 目标

- 在入门级 8GB Apple Silicon 上为 8K 图片和 500 个评审标记提供稳定、可预测的缩放和平移。
- 把图片、所有评审几何、编号、选择状态和放大镜统一为一个场景、一条坐标变换链和一个帧调度器。
- 让相机变化只修改小型 GPU 常量，不触发 React 重渲染、DOM 布局读取、完整 Canvas 重建或图片重解码。
- 通过分级清晰度、可取消任务、可见区域优先和统一内存预算控制大图资源。
- 让评审保存只提交变化记录；保存后原地更新场景，不出现加载页、白屏或完整工作区重载。
- 保持现有 Review、Anchor、revision、存档、历史、发布和 Agent 读取协议的含义与格式。
- 建立可测试的渲染端口，使 UI、领域状态、GPU 实现和平台窗口生命周期能够独立演进。

## 4. 非目标与冻结契约

### 4.1 非目标

本轮不包含：

- 新增图片评审工具、调整工具含义或改变现有视觉样式；
- 改造网格缩略图、对比预览或视频播放引擎；
- 实现视频时间点／时间段标注；
- 实现 Windows 渲染后端；
- 引入云端渲染、同步、遥测或远程缓存；
- 修改评审数据迭代、存档或 Agent 交接的产品逻辑；
- 新增 HDR 编辑或专业调色能力；
- 签名、公证、正式安装包、上架或发售。Viewer 仍处于开发初期，这些事项不是本轮任务、验收项或
  默认后续建议。

### 4.2 用户可见行为冻结

以下行为必须保持不变：

- 工具名称、工具切换、快捷键、鼠标语义、触控板语义和焦点顺序；
- 适应窗口、自由缩放、旋转、平移、放大镜以及上一张／下一张导航结果；
- 标记外观、编号、选择、重绘、文字编辑、删除和意见栏联动；
- 默认图片几何尺寸和不同长宽比之间的显示关系；
- 文案、保存成功／失败语义、历史和存档入口；
- 评审数据、公开证据、Agent 读取结果和协议版本。

渐进加载只允许提高清晰度，不得改变图片在视口中的几何位置、尺寸、旋转或标记投影，不得产生可见的
页面跳转、加载页闪烁或白屏。

## 5. 总体架构与依赖边界

目标结构如下：

    React / Tauri 产品外壳
      工具栏 · 意见栏 · 历史 · 文本编辑器 · 页面导航
                   |
                   | 语义命令与语义事件
                   v
              RendererPort
             /            \
       迁移期 Web 实现    原生视口适配器
                               |
                               v
        macOS 原生宿主 + 输入路由 + 显示刷新驱动
                               |
                               v
          平台无关渲染核心 -> wgpu 渲染器 -> Metal
                    |              |
                    v              v
              场景与相机      纹理、管线与缓存
                    ^
                    |
           图片资源与解码工作线程

建议建立以下清晰边界：

- viewer-render-core：平台无关的场景、相机、坐标、LOD、资源请求、命中检测、命令和事件模型。
  不依赖 AppKit、Metal、Tauri、React、SQLite 或评审存储。
- viewer-render-wgpu：依赖 viewer-render-core 和 wgpu，拥有 GPU 设备、队列、管线、纹理、缓冲区、
  帧图和缓存实现。核心渲染代码不出现 AppKit 或 Tauri 类型。
- viewer-platform-macos：建立原生视图、Metal surface、窗口生命周期、显示刷新、输入路由、色彩空间
  和内存压力适配。macOS 专有类型不得泄漏到渲染核心。
- viewer-desktop：继续作为具体实现的唯一装配点，组合 Tauri、平台宿主、资源提供者和渲染会话。
- UI RendererPort：位于前端呈现边界。迁移期由现有 Web 渲染适配器和原生桥接适配器共同实现；
  切换实现不改变上层工作台组件的意图和评审数据。

评审数据库和领域状态始终是权威来源。GPU 场景只是带版本号的只读投影，渲染器无权修改 SQLite、
公开评审文件或 Agent 可读状态。评审保存和发布任务也不得等待 GPU 帧完成。

## 6. 原生视口组合与职责

macOS 窗口在同一内容根视图中组合 WKWebView 和原生 Metal 视口。原生视口只占据图片预览区域；
工具栏、意见栏、历史和导航继续由 React 绘制。窗口布局变化时，前端只提交稳定的预览区域和需要位于
原生视口之上的交互排除区域，不参与每一帧布局。

输入职责固定如下：

- 原生视口直接接收鼠标、触控板、缩放、拖动和标记编辑手势；
- 渲染线程负责相机、命中检测、标记拖动、放大镜位置和当前帧；
- React 负责工具选择、意见列表、文本输入、对话框和导航；
- 内联评审文本框仍由 React 管理。原生视口发送草稿锚点和稳定后的屏幕位置，平台输入路由保证
  文本框区域接收 Web 输入，其余预览区域交给原生视图；
- 连续事件按显示帧合并，禁止为每次指针移动发送一次 Tauri IPC；
- React 只接收“选择改变”“草稿创建”“几何提交”“视口稳定”“渲染错误”等语义事件。

主线程只负责 AppKit 视图生命周期、输入采集和必要布局。渲染执行器独占 GPU 设备、队列、surface、
场景投影和资源缓存；解码工作池负责图片派生。三者之间使用有界队列：相机和指针状态采用最新值覆盖，
不可形成积压；需要持久化的语义命令必须有命令 ID 和确认结果。

## 7. 场景模型与统一坐标

### 7.1 保留式场景

每个原生图片会话维护一个保留式 SceneSnapshot，至少包含：

- 当前素材身份、已应用方向后的宽高和色彩描述；
- CameraState：适窗基准、用户缩放、平移、旋转和视口尺寸；
- 已提交评审图元及其稳定 ID、意见编号和 revision；
- 当前选择、临时绘制、调整手柄和保存状态；
- 放大镜的形状、面积、倍率、采样点和可见状态；
- asset_generation、scene_revision 和 resource_generation。

场景更新使用不可变快照或显式差量。相机变化不重建标记几何；意见文字变化不重新上传图片；图片切换
必须提高 asset_generation，使旧图片的解码、上传和事件结果自动失效。

### 7.2 唯一变换链

所有图片和评审图元统一经过以下坐标空间：

    已应用 EXIF 方向的规范化图片坐标
      -> 源图片像素坐标
      -> 场景世界坐标
      -> 视口逻辑点
      -> drawable 物理像素

评审 Anchor 按现有协议继续存储在规范化图片坐标中。图片、矩形、圆圈、箭头、画笔、编号、命中检测、
调整手柄和放大镜都必须调用同一组纯变换函数，禁止组件自行推导比例、旋转方向或设备像素倍率。

适窗基准只使用以下输入：

- 应用 EXIF 方向后的图片长宽比；
- 当前真实可用预览区域；
- 产品既有的安全边距规则。

原图像素尺寸、文件体积、人物或商品在画面中的占比、透明边缘和视觉内容不得进入适窗几何算法。
像素尺寸只用于决定当前缩放下需要哪个清晰度层级。

### 7.3 放大镜

放大镜是同一场景的第二个观察视口，而不是第二份图片或第二套标注系统。它使用相同纹理、图元缓冲和
坐标变换，只改变相机采样区域、倍率和裁切形状。镜片内同时显示图片与评审标记，编号保持可读尺寸，
轮廓宽度遵守现有视觉上限；镜片不复制整张原图纹理，也不重新解释 Anchor。

## 8. 图片资源、清晰度层级与缓存

### 8.1 用户可感知的数据流

打开图片时按以下顺序工作：

1. 读取尺寸、方向、色彩空间和稳定文件身份，不同步解码完整原图。
2. 根据视口物理尺寸生成或读取适窗代理图，目标覆盖当前视口所需像素并留出小幅缩放余量。
3. 代理图一旦可用便显示可交互画面；清晰度提升不能改变几何或阻塞手势。
4. 调度器依据当前缩放、可见区域和移动方向请求更高精度内容。
5. 当前画面优先，其次是移动方向前方和邻近区域，远离视口的任务可以取消。
6. 高清资源完成后在帧边界原子替换，禁止闪白、跳屏或重新进入页面加载状态。

冷启动目标是在 300 ms 内给出可交互适窗画面；派生缓存命中时目标为 100 ms 内。若源文件或存储设备
无法满足目标，界面仍应保持响应，并通过既有加载状态表达进度，不能阻塞窗口事件循环。

### 8.2 单纹理与分块策略

资源策略依据解码后的预计占用和设备能力，而不是简单依据文件大小：

- 完整纹理及 mip 层预计占用不超过当前图片预算的四分之一、单边尺寸不超过设备限制时，使用一张纹理
  及其 mip 层；
- 超过该条件时使用 512 × 512 源像素瓦片和多级金字塔；边缘瓦片允许不足尺寸，并使用防接缝边界；
- 当前 wgpu 路径使用通用瓦片图集，不要求稀疏纹理；未来只有在真实分析证明收益后，才允许在 macOS
  平台适配器内增加 Metal 稀疏资源优化；
- 普通图片和超大图片对上层暴露完全相同的场景及交互语义。

可见清晰度按“一个屏幕物理像素需要多少源像素”选择最接近且不低于需求的层级。系统只加载当前缩放
真正需要的精度；用户继续放大时再补充更细层级，缩小时不保留无用的最高精度资源。

### 8.3 缓存与内存预算

- CPU 解码资源、上传暂存和 GPU 纹理由一个资源协调器统一记账，避免在 Apple 统一内存上分别计算后
  实际超额占用；
- 8GB 基线配置中，常驻图片 GPU 纹理预算默认不高于约 256 MiB，并响应 macOS 内存压力动态收缩；
- 当前可见瓦片和放大镜所需瓦片具有最高优先级，最近使用资源按 LRU 回收；
- 管线、采样器、通用图元缓冲和当前帧资源长期复用，采用至少三份帧内暂存区，禁止每帧重新创建；
- 磁盘派生缓存按内容身份、方向、色彩转换版本和解码器版本寻址，位于可安全删除的应用缓存目录，
  不写入或污染用户素材目录；
- 缓存缺失、损坏或版本不匹配等价于未命中，不能改变源文件或评审数据。

### 8.4 色彩与方向

Image I/O／ColorSync 继续负责读取 EXIF 方向和嵌入式色彩描述。资源提供者在纹理生成前完成确定性的
方向和工作色彩空间转换，最终 drawable 使用当前显示器适配的色彩空间。相同输入、相同显示配置下，
新旧引擎必须通过视觉基准；本轮不借机增加 HDR 或新的色彩编辑行为。

## 9. 帧调度、图元与命中检测

- macOS 显示刷新驱动提供实际刷新节奏；60 Hz 设备以 16.7 ms 为帧预算，支持高刷新率的设备不被
  算法固定在 60 Hz；
- 没有动画、交互或资源更新时不持续空转；有交互时每个显示周期最多提交一帧；
- 相机只通过小型 uniform 更新，图片纹理和不变标记缓冲不重复上传；
- 标记几何按 scene_revision 缓存。只有创建、重绘、调整或删除标记时才重新生成受影响图元；
- 画笔和矢量图元在 CPU 侧生成稳定几何，GPU 负责视口变换、裁切和合成；
- 命中检测在规范化图片坐标中使用空间索引，先进行粗筛，再对候选图元做精确判断；
- 放大镜复用当前场景和纹理，通过第二次绘制与裁切实现，不建立第二份完整图像；
- 图片、标记、编号、选择状态和放大镜在同一帧使用同一个 SceneSnapshot，避免一帧错位。

## 10. RendererPort 与消息协议

RendererPort 只暴露稳定语义，不暴露 DOM、AppKit、Metal 或 wgpu 对象。迁移期间两种实现必须消费
同一组上层意图。最低命令集合包括：

- 打开／关闭素材会话；
- 设置工具、适窗、缩放步进、旋转和意见栏可见区域；
- 替换完整场景快照；
- 应用评审差量；
- 聚焦、重绘或删除指定标记；
- 设置内联编辑器交互排除区域；
- 请求诊断快照或会话关闭。

最低事件集合包括：

- 原生视口就绪；
- 选择改变；
- 标记草稿创建或几何调整完成；
- 稳定后的视口状态；
- 资源清晰度达到当前需求；
- 可恢复或阻断型渲染错误。

每条消息携带 session_id；素材相关消息同时携带 asset_generation；场景差量携带 scene_revision。
持久化语义命令还携带 command_id。接收方必须丢弃过期 generation，幂等处理重复 command_id，
并在 revision 不连续时请求完整场景重新同步，不能猜测缺失状态。

## 11. 评审创建与保存链路

评审操作采用草稿、持久化确认、场景提交三个明确阶段：

1. 用户完成一次绘制后，原生场景立即显示带稳定草稿 ID 的临时标记，不写数据库。
2. 原生视口发送“标记草稿创建”事件，React 在既有位置打开内联文字编辑器。
3. 用户保存时，UI 向现有评审应用服务发送带 command_id、当前轮次和预期 revision 的语义命令。
4. 应用服务只提交该条变化及其逻辑状态，不扫描项目、不重新解码图片、不生成图片证据，也不等待 GPU。
5. 持久化成功返回新的权威 revision 和最小 ReviewPatch。UI 与原生场景就地把草稿转成已提交标记，
   意见栏应用同一差量，不重新加载完整工作区。
6. 持久化失败时保留草稿文字和几何，显示既有错误并允许重试；不得把未持久化内容显示成已保存。

编辑文字、重绘、调整区域和删除使用同一条差量链路。单条评审的交互反馈应在下一显示帧出现；本地正常
存储条件下，逻辑提交的第 95 百分位目标不高于 100 ms，第 99 百分位目标不高于 300 ms。超过 150 ms
可以显示非阻塞保存状态，但不能切换到加载页面或冻结预览。

此处只改变渲染同步方式，不改变已批准的快速评审保存、后台物化、存档和 Agent 发布安全协议。

## 12. 故障处理与恢复

### 12.1 迁移期

- 新引擎初始化失败，或同一会话内连续两次自动资源恢复失败时，可以自动切回旧渲染器；
- 回退只更换显示实现，评审领域状态、未提交文字和已保存数据不回滚；
- 本地诊断记录稳定错误码、设备能力、资源预算、最近场景 revision 和恢复次数，不记录素材内容或
  评审文字；
- 可按本次会话或开发开关选择新旧实现，默认切换必须由验收门禁决定。

### 12.2 稳定后

旧渲染器删除后，不增加轻量 CPU 预览兜底。窗口尺寸改变、显示器切换、休眠唤醒、surface 失效或
GPU device lost 时，新引擎按以下顺序恢复：

1. 暂停提交新帧并保留 CPU 侧 SceneSnapshot 和草稿；
2. 重建 surface、设备相关管线和 GPU 缓存；
3. 按当前场景和可见区域重新请求资源；
4. 首帧成功后恢复输入并继续原会话。

恢复失败时显示阻断型 GPU 渲染错误，不伪装为可继续使用。评审数据库、公开协议和已提交记录不受影响；
仍在内存中的草稿保持可恢复，直到用户关闭会话或应用退出。

## 13. 性能门禁

最低性能基线为 8GB 内存的入门级 Apple Silicon，而不是当前开发机的 M4。删除旧引擎前必须满足：

- 8K 图片和 500 个评审标记下，持续缩放和平移保持 60 FPS；
- 在 60 Hz 测试中，第 95 百分位帧时间不超过 16.7 ms，不以平均值掩盖卡顿；
- 支持 120 Hz 的设备尽可能跟随实际刷新率，内部调度不得固定在 60 Hz；
- 冷启动 300 ms 内提供可交互适窗画面，派生缓存命中时目标为 100 ms 内；
- 交互期间不进行同步完整原图解码、不重分配全屏 Canvas、不等待磁盘或评审持久化；
- 8GB 基线下常驻图片 GPU 纹理默认不超过约 256 MiB，并在内存压力下可观察地回收；
- 开启放大镜后仍满足同一帧预算，且不存在第二份完整原图纹理；
- 连续切图、缩放、旋转和放大镜移动不会形成过期解码任务或无界消息队列。

性能测试必须报告帧时间分布、主线程占用、GPU 提交时间、纹理峰值、CPU 解码峰值、瓦片命中率和
取消任务数量。只观察“感觉流畅”不能作为通过依据。

## 14. 迁移阶段

### 阶段 1：边界与基准

- 建立 UI RendererPort、原生消息协议和确定性的场景／坐标类型；
- 为现有用户行为建立交互回放、视觉基准和性能基线；
- 现有 Web 渲染器仍为默认实现，不改变用户行为。

### 阶段 2：原生图片视口

- 接入 macOS 原生视图、wgpu Metal surface、显示刷新和输入路由；
- 实现图片显示、适窗、缩放、平移、旋转和快速图片切换；
- 先使用单纹理路径验证帧循环和窗口生命周期，再接入资源调度。

### 阶段 3：复合评审场景

- 迁移所有现有标记、编号、选择、命中检测、草稿、重绘和调整；
- 迁移放大镜为同一场景的第二视口；
- 接入 React 内联编辑器和意见栏语义事件，不修改评审协议。

### 阶段 4：分级资源与缓存

- 接入快速代理图、单纹理／瓦片决策、多级金字塔、预取、取消和 LRU；
- 接入统一内存预算、色彩管理和内存压力处理；
- 完成 8K 与大量标记的性能门禁。

### 阶段 5：隐藏对照与稳定性

- 在开发开关下对同一测试输入运行新旧实现；
- 完成视觉差异、交互事件、坐标、性能、休眠唤醒、设备恢复和长时间压力测试；
- 新引擎仍可按会话回退，所有阻断问题必须在切换默认前解决。

### 阶段 6：单引擎收口

- 连续两轮完整验收没有阻断问题后，将新引擎设为唯一实现；
- 删除旧图片预览和评审热路径、迁移开关及只服务旧路径的兼容代码；
- 保留 RendererPort、场景协议和平台边界，为未来对比视口与 Windows 后端复用；
- 不实施签名、公证、正式安装包、上架或发售工作。

## 15. 测试与验收

### 15.1 纯算法测试

- 对全部图片比例、四个旋转角度、不同窗口尺寸和设备像素倍率验证适窗结果；
- 使用随机化和性质测试验证规范化坐标与视口坐标往返、命中检测和标记不漂移；
- 验证 LOD 选择、瓦片覆盖、预取优先级、取消、LRU 和预算收缩；
- 验证 generation、revision 和 command_id 的过期、重复、乱序与重新同步规则。

### 15.2 渲染与视觉测试

- 为横图、竖图、方图、超宽图、超高图、透明图、带方向信息和不同色彩描述的图片建立金图；
- 覆盖全部评审工具、编号、选中、草稿、手柄和放大镜；
- 比较适窗、不同缩放、平移、旋转和高 DPI 下的截图与几何测量；
- 渐进清晰度替换前后图片边界和标记位置必须逐像素稳定，瓦片边缘不得出现接缝。

### 15.3 交互与数据测试

- 回放现有鼠标、触控板、快捷键、切图和意见编辑流程，比较新旧 RendererPort 的语义事件序列；
- 验证保存成功后只应用 ReviewPatch，不出现完整工作区重载；
- 验证保存失败保留草稿，重复提交幂等，过期确认不覆盖新状态；
- 验证 React 文本框焦点、按钮点击、原生手势和输入排除区域不存在争抢；
- 验证切换素材后旧图片的解码、上传、命中和保存返回不能进入当前会话。

### 15.4 平台与压力测试

- 覆盖窗口连续缩放、全屏切换、Retina 倍率变化、外接显示器、休眠唤醒和 device lost；
- 在资源预算附近反复打开不同尺寸图片，确认内存回落且不存在纹理泄漏；
- 运行 30 分钟连续缩放、平移、切图和放大镜压力测试；
- 使用现有“下载／测试图”素材库做只读真实验收，测试不得修改或生成文件到原始素材目录；
- 完整 Rust 测试、前端单元与集成测试、架构边界检查、类型检查、静态检查和生产构建全部通过。

只有连续两轮完整验收无阻断问题，才允许执行阶段 6。
