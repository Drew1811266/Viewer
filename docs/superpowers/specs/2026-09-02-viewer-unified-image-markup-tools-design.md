# Viewer 统一图片标记工具设计

> Status: Approved
>
> 日期：2026-09-02
>
> 类型：图片评审工作台标记能力与 Agent 协议演进
>
> 设计确认：范围、交互、统一标记菜单、快捷键、数据语义、渲染架构、保存与失败恢复已逐节确认。

## 1. 结论

Viewer 在既有画笔、矩形和整图意见之上，新增点标记、箭头和椭圆三种图片定位方式，并把
所有局部标记收拢到一个固定名称的“标记”菜单中。

新增能力不是三组临时画布分支。图片局部意见继续遵守“一条自然语言意见 + 一个明确 Anchor”
的原子语义；所有工具共享同一坐标系统、编辑状态机、只读场景、保存增量和 Agent 发布链路。
这样既避免工具增多后工具栏持续膨胀，也避免同一问题在 UI、历史记录与 Agent 数据中出现
三种不一致解释。

本设计扩展并部分取代
[图片标注评审工作台设计](2026-08-26-viewer-image-annotation-review-workbench-design.md)中把箭头和
椭圆列为非目标的边界；该文档的自然语言权威、Feedback 身份、规范化坐标、安全资源边界、
原图不修改和保存原子性继续有效。本设计同时继承
[复合评审放大镜设计](2026-09-01-viewer-composite-review-magnifier-design.md)与
[快速评审保存设计](2026-09-01-review-save-pipeline-design.md)。

## 2. 背景与问题

当前工作台只有画笔和矩形：

- 一个精确的小位置通常需要画一个不自然的圈或很小的矩形；
- 方向性问题无法明确表达“从哪里指向哪里”；
- 圆形或人物局部区域只能用矩形近似，边界语义较粗；
- 画笔和矩形分别占据顶栏入口，后续继续增加工具会挤压缩放、放大镜、意见栏和历史入口；
- 现有 `AnnotationCanvas` 的手势、绘制和编辑逻辑围绕两个工具直接分支，继续堆叠条件判断会
  放大缩放命中、放大镜投影、保存状态与快捷键之间的耦合；
- 当前 `ReviewAnchor`、Rust Domain、Tauri DTO、持久化协议和 JSON Schema 都是封闭联合类型，
  仅修改画面而不扩展端到端模型会让 Agent 无法可靠区分标记语义。

因此，本轮既是用户可见的标记工具扩充，也是一次受控的 Anchor 能力演进。

## 3. 目标与非目标

### 3.1 目标

1. 新增点、箭头和椭圆，覆盖精确目标、方向指向和闭合区域三类常见评审表达。
2. 保留画笔、矩形和整图意见的既有语义与数据。
3. 用可扩展的统一“标记”菜单容纳全部局部标记工具。
4. 所有工具在缩放、平移、旋转、临时平移和放大镜中保持几何一致。
5. 保存只提交一条意见的逻辑增量，不重新加载图片或重建工作台。
6. 为 Agent 输出明确、稳定、可验证的 Anchor 类型，不依赖图片内容或自然语言推断几何。
7. 保持旧 `viewer.review/3` 状态、存档和证据不可变且可读。
8. 为后续直线、多边形等工具建立窄扩展点，但不提前实现它们。

### 3.2 非目标

- 不新增直线、多边形、套索、文字贴纸、印章、模糊、裁剪或像素编辑。
- 不新增标记颜色、线宽、透明度和箭头样式设置。
- 不新增视频时间点或时间段标注界面。
- 不做 AI 自动定位、自动归类、自动改写意见或自动判断问题是否解决。
- 不改变“用户只对需要返工的素材写意见；未评价素材没有当前返工要求”的产品语义。
- 不自动通知、启动或调度外部 Agent。
- 不实现多人协作或云同步。
- Viewer 仍处于开发初期。本轮不包含代码签名、Apple 公证、正式安装包、上架、公开发布或
  发售，这些事项也不是默认收尾任务。

## 4. 采用方案与取舍

### 4.1 工具范围

采用第一批：点、箭头、画笔、矩形、椭圆。

| 工具 | 权威定位语义 | 适用情况 |
| --- | --- | --- |
| 点 | 精确目标点 | 小瑕疵、局部像素、五官或文字错误 |
| 箭头 | 从尾部指向箭头端点；端点是目标 | 方向、偏移、对应关系、需要移动到的位置 |
| 画笔 | 不规则追踪路径 | 轮廓、褶皱、连续边缘、不规则缺陷 |
| 矩形 | 矩形包围区域 | 规则区域、版面块、局部构图 |
| 椭圆 | 椭圆包围区域 | 人脸、关节、圆形物体或柔和范围 |

暂不加入直线和多边形。直线与箭头高度重叠；多边形的节点编辑、闭合规则和键盘可访问性
会显著扩大本轮范围。文字始终写入意见栏／就地编辑器，不在画布上生成第二份可漂移文本。

### 4.2 工具入口

采用固定“标记”按钮，不采用“最近工具替换主按钮”或长按菜单：

- 顶栏始终显示同一个“标记”名称和图标；
- 点击总是打开完整菜单；
- 菜单按照点、箭头、画笔、矩形、椭圆排列；
- 选择后关闭菜单；
- 任一标记工具激活时，“标记”按钮使用现有蓝色激活态；
- 重新打开菜单时，当前工具显示选中状态；
- 点击菜单外只关闭菜单，不改变当前工具；
- 只读状态仍可打开菜单查看工具，但写入工具不可激活并解释只读原因。

该方案多一次菜单点击，但入口含义稳定、可发现性强，也为后续工具扩展保留空间。

## 5. 用户交互

### 5.1 点标记

1. 用户选择“点”。
2. 在真实图片区域单击一次。
3. 立即出现临时点标记与编号，并在不遮挡目标的位置打开意见编辑器。
4. 非空文字和有效点一起保存，二者缺一不形成 Feedback。
5. 已保存的点可以拖动；调整几何时保留 Feedback ID、文字和编号投影身份。

点的权威位置就是单击点。编号徽章使用屏幕空间偏移显示，不改写 Anchor；接近图片或窗口
边缘时在候选方向中翻转，优先避免盖住目标和超出可视区域。

### 5.2 箭头

1. 用户从箭尾按下并拖向问题目标。
2. 指针释放位置形成箭头端点，也是 Agent 语义中的 `head`／目标。
3. 有效箭头形成临时编号并打开意见编辑器。
4. 已保存箭头在选中后显示尾部和端点两个控制手柄，两个端点都可独立调整。

短于 6 CSS px 的创建手势按误触取消。该阈值只约束当前手势；Domain 的永久不变量是两个
规范点不同，避免持久数据合法性依赖窗口缩放。编号默认靠近尾部，不能覆盖箭头端点。

### 5.3 椭圆

1. 用户拖出椭圆的外接框。
2. 默认无填充，只使用当前高对比评审轮廓。
3. 按住 Shift 时约束为视觉圆形。约束在校正方向后的源图像素空间计算，而不是错误地令
   归一化宽高相等。
4. 已保存椭圆可整体移动，并通过外接框四角控制手柄缩放。

小于 6 × 6 CSS px 的创建手势取消。Domain 只要求外接框有限、宽高为正且不越界。编号使用
外接框候选角点，并通过通用避让算法选择不遮挡目标的一侧。

### 5.4 公共行为

- 保存后当前工具保持激活，适合连续标注同类问题。
- `V` 返回浏览；`Esc` 在有草稿时取消草稿，没有草稿时返回浏览。
- 空格只在按住期间临时平移，松开恢复原工具。
- 图片以外的单击不创建或裁剪标记。
- 指针离开 Canvas 后仍通过 Pointer Capture 完成或取消当前手势，不能留下半个图形。
- 点击画布标记与点击意见栏条目继续双向选择同一 Feedback。
- 当前轮保存后的标记始终可编辑；存档只冻结历史快照，不锁定当前工作台。
- 切换图片、返回网格或关闭窗口时若存在未保存草稿，必须保存或明确放弃。

### 5.5 快捷键

| 快捷键 | 行为 |
| --- | --- |
| `V` | 浏览 |
| `P` | 点 |
| `A` | 箭头 |
| `B` | 画笔 |
| `R` | 矩形 |
| `O` | 椭圆 |
| 按住空格 | 临时平移 |
| `Esc` | 取消草稿；无草稿时返回浏览 |
| `Command/Ctrl + Enter` | 保存当前意见 |
| 椭圆绘制时按住 Shift | 约束为视觉圆形 |

输入框、下拉框、可编辑元素获得焦点时不处理单键工具快捷键。组合键和输入法合成过程也不
触发工具切换。

## 6. 状态机与工具扩展边界

### 6.1 工具选择与编辑阶段分离

当前工具不能继续隐含在“编辑器回到 idle 就重置为 browse”的状态中。拆为两个正交状态：

```text
activeTool = browse | point | arrow | brush | rectangle | ellipse

editorPhase =
  idle
  | drawing
  | editingText
  | editingGeometry
  | saving
  | saveError
```

保存成功只把 `editorPhase` 变为 `idle`，不改变 `activeTool`。临时平移是独立的按键覆盖状态，
不修改以上两个权威值。

### 6.2 工具注册表

建立编译期 `AnnotationToolRegistry`，而不是运行时插件系统。每个工具描述符只声明：

- 稳定工具 ID、名称、图标和快捷键；
- 是否需要拖拽；
- 手势创建策略；
- Anchor 基本验证；
- 选中后的编辑策略；
- 菜单排序和可用性。

通用控制器负责输入所有权、Pointer Capture、草稿生命周期、文字绑定、保存、取消、只读、
快捷键和菜单状态。工具策略不能调用 Review API、修改评审轮次或直接序列化协议。

### 6.3 明确状态转换

```text
idle + tool gesture
  → drawing / editingText
  → valid geometry + nonblank text
  → saving
  → idle with same activeTool

saving → saveError
saveError → retry → saving
saveError → edit → editingText / editingGeometry
dirty phase + navigation → explicit save or discard
```

任何时刻最多只有一个未保存的 Feedback 草稿。切换工具前若草稿为空可直接取消；若已有
几何或文字，不静默丢弃。

## 7. 坐标、命中检测与编辑

### 7.1 单一坐标管线

所有工具必须使用 `ImagePreviewProjection` 的同一转换链：

```text
屏幕 CSS 坐标
  → 舞台坐标
  → 校正方向后的源图坐标
  → [0, 1] × [0, 1] 规范坐标
```

持久 Anchor 与图像像素值、预览初始大小、窗口大小、设备像素比、缩放、平移和临时旋转
无关。渲染、编辑和命中检测都从同一规范 Anchor 重新投影，禁止各工具复制一套比例算法。

### 7.2 通用命中检测

命中检测在规范几何上定义，但把统一的 8 CSS px 指针容差通过当前逆投影换算到源图空间：

- 点：目标点附近；
- 箭头：优先端点手柄，其次线段；
- 画笔：到任一路径线段的最短距离；
- 矩形／椭圆：优先控制手柄，其次轮廓，最后内部移动区域；
- 多条标记重叠时：控制手柄 > 当前选中项 > 编号徽章 > 最近轮廓 > 后绘制项。

命中排序必须确定，不能依赖 DOM 顺序偶然变化。编号徽章属于交互投影，可选择 Feedback，
但不属于 Anchor 几何。

### 7.3 几何规则

- 所有数字必须有限并位于闭区间 `[0, 1]`。
- 点允许位于图片边界。
- 箭头尾部和端点必须不同，两个点均在图片内。
- 椭圆复用严格的规范外接框约束：`width > 0`、`height > 0`、右下边界不超过 `1`。
- 拖动越界时在交互层保持整体尺寸并约束至边界；调整手柄时只约束活动端。
- 不把屏幕像素阈值保存进 Domain，也不依据图像内容自动改变 Anchor。

## 8. Anchor 领域模型与 Agent 语义

### 8.1 UI／Tauri DTO

TypeScript 与 Tauri 命令边界扩展为：

```ts
type ReviewAnchor =
  | { kind: 'asset' }
  | { kind: 'image_point'; x: number; y: number }
  | {
      kind: 'image_arrow'
      tail: { x: number; y: number }
      head: { x: number; y: number }
    }
  | { kind: 'image_stroke'; points: ReadonlyArray<{ x: number; y: number }> }
  | { kind: 'image_rect'; x: number; y: number; width: number; height: number }
  | { kind: 'image_ellipse'; x: number; y: number; width: number; height: number }
  | { kind: 'video_point'; positionUs: number }
  | { kind: 'video_range'; startUs: number; endUs: number }
```

箭头使用嵌套 `tail` 和 `head`，避免四个扁平坐标在调用方被交换。Tauri DTO 继续使用
`snake_case` kind 与 `camelCase` 字段的现有边界约定。

### 8.2 Domain

Rust Domain 新增：

```text
FeedbackAnchor::ImagePoint(NormalizedPoint)
FeedbackAnchor::ImageArrow(NormalizedArrow { tail, head })
FeedbackAnchor::ImageEllipse(NormalizedRect)
```

`ImageEllipse` 可以复用 `NormalizedRect` 值对象做边界验证，但必须保留独立枚举类型；矩形和
椭圆对 Agent 的区域语义不同。`NormalizedArrow` 构造时拒绝相同端点。

Domain 不知道线宽、颜色、编号位置、菜单、缩放、Canvas 或放大镜。它只保证数学合法性、
媒体类型、目标身份和 Feedback 不变量。

### 8.3 Agent 可读语义

对外持久格式使用稳定的 camelCase kind：

```json
{ "kind": "imagePoint", "x": 0.42, "y": 0.31 }
{ "kind": "imageArrow", "tail": { "x": 0.2, "y": 0.4 }, "head": { "x": 0.42, "y": 0.31 } }
{ "kind": "imageEllipse", "x": 0.3, "y": 0.2, "width": 0.25, "height": 0.18 }
```

读取文档必须明确：

- `imagePoint` 的坐标是精确目标；
- `imageArrow.head` 是箭头指向的目标，`tail` 只提供方向和上下文；
- `imageEllipse` 表示椭圆内部区域；
- `imageRect` 表示矩形内部区域；
- `imageStroke` 表示沿路径指出的不规则位置；
- 自然语言原文始终是修改要求的权威，Anchor 只负责定位。

Agent 不需要从渲染 PNG、文件名、图片内容或意见文字猜测工具类型。表现属性不进入语义
协议。

### 8.4 身份和历史

- 修改当前意见几何时保留 Feedback ID 和列表序号投影；目标修订 ID 按既有规则更新。
- 同一意见的文字和 Anchor 可以分别产生修订，但一个公开快照始终引用完整一致的组合。
- 删除、调整和重画只作用于当前状态。
- 手动存档冻结当时的 Anchor、自然语言、素材版本和证据。
- “继续提出”从历史创建新的当前 Feedback，不原地修改历史。
- 旧版本意见不会因新图相似、文件同名或新工具可用而自动转换 Anchor。

## 9. 协议演进与兼容

### 9.1 为什么需要 `viewer.review/4`

`viewer.review/3` 的 Anchor JSON Schema 是关闭的 `oneOf`，Rust 线格式也启用了严格未知字段
拒绝。直接在 v3 联合类型中追加新 kind，会让仍按 v3 契约运行的旧读取器遇到它不理解的
数据，属于静默破坏协议。

因此：

- `viewer.review/3` 的既有状态、索引、存档、读取结果与 Schema 保持不可变；
- 新增 `viewer.review/4` 状态、索引、存档和读取结果 Schema；
- v4 是持续评审生命周期的协议升级，不改变当前／历史／待确认／发布头语义，只扩展 Anchor；
- 新版原生读取器同时读取 v3 和 v4；当前状态与精确历史读取结果保留其来源协议版本，
  v3 状态输出 v3 结果，v4 状态输出 v4 结果；
- 旧 v3 历史文件保留原位置、原字节和原摘要，不就地重写；
- 只包含旧 Anchor 的 v3 项目继续生成 v3 快照，不因打开项目或升级应用而写盘；
- 项目第一次成功保存任一 v4 Anchor 时，authoring snapshot 明确记录目标协议为 v4，
  Materializer 以新的不可变 v4 状态和原子索引发布进入 v4；
- 项目进入 v4 后，后续快照始终保持 v4，即使后来删除了全部新型 Anchor，也不降级或来回
  切换协议版本。

v4 Schema 对所有 Anchor 分支继续使用严格字段、数值边界、数组上限和文档大小上限。所有
Schema、Rust 编解码、Node 协议测试、CLI 读取结果和产品协议文档必须在同一提交序列内演进。

### 9.2 旧数据

- v3 的 `asset`、`imageRect`、`imageStroke`、`videoPoint`、`videoRange` 无损映射到同语义 v4。
- 旧标记不自动转换成点、箭头或椭圆。
- v3 存档和精确历史选择器继续可读。
- 任何无法无损解码或摘要不匹配的数据继续返回类型化完整性错误，不降级猜测。
- 证据渲染器版本随新增形状显式升级；旧证据对象继续按原摘要引用，不重新伪造。

## 10. 渲染与放大镜

### 10.1 共享只读场景

`buildAnnotationScene` 扩展三种新 Anchor；舞台画布和放大镜 Painter 继续消费同一个只读场景。
场景渲染顺序固定为：

1. 已保存标记；
2. 当前选中标记；
3. 正在创建或调整的临时标记；
4. 编号投影。

交互控制手柄和文字编辑器不进入只读场景，避免被放大镜复制或参与证据输出。

### 10.2 复合放大镜

图片、已保存标记和当前临时几何作为一个复合观察层被放大镜采样：

- 新形状与图片使用同一 `normalizedToLens` 投影；
- 箭头端点、曲线和椭圆轮廓在镜片内保持位置一致；
- 线宽按倍率增长但继续限制在现有 2–5 CSS px；
- 编号保持固定可读尺寸；
- 编辑手柄、输入框、菜单和意见栏不放大；
- 镜片 `pointer-events: none`，不抢占工具手势或标记选择；
- 图片和标记在同一动画帧消费同一投影快照。

### 10.3 原生证据

Agent 证据预览必须能确定性渲染三种新形状，并与 UI 使用相同的锚点语义和编号投影规则。
原生渲染器不复制 UI 像素布局，但必须保持：箭头端点含义、椭圆外接框、点目标、编号对应
关系和方向校正一致。原图永不被修改。

## 11. 保存、发布与失败恢复

### 11.1 前台保存

复用现有 `ContinuousReviewAuthoringService`、SQLite AuthoringStore、命令幂等性和最小
`ReviewWorkspacePatch`：

1. UI 保留临时几何和文字。
2. 保存命令携带稳定 command ID、expected revision 和一个完整 Anchor。
3. Domain 在内存副本上验证转换。
4. AuthoringStore 在一个短事务中提交逻辑快照、转换和 materialization outbox。
5. 返回最小 Patch；UI 原地把草稿替换为已保存项并关闭编辑器。
6. 当前工具、图片解码结果、缩放、平移、放大镜和意见栏状态不变。

不得为新 Anchor 建立第二套保存队列，也不得在前台等待 PNG 渲染、全工程扫描、完整 JSON
重载或 Agent 发布。继续沿用正常 ≤64 KiB 新逻辑命令的目标预算：p50 ≤50 ms、p95 ≤150 ms、
p99 ≤300 ms；证据生成不计入前台确认预算。

### 11.2 后台发布

- Materializer 读取精确 authoring revision，生成需要的新标记证据并发布不可变 v4 状态。
- 同一 Feedback 的快速连续更新按 authoring 序列处理；旧作业可以被新快照合并或跳过，但
  绝不能在新状态之后发布旧状态。
- 只有 `authoring_head == published_head` 时，当前 Agent 读取成功。
- 发布尚未追上时返回 `publication_pending`，不把旧状态冒充最新状态。
- 精确、已发布的历史选择器继续可读。

### 11.3 失败行为

- 前台事务失败：保留几何和文字，显示“未保存，可重试”；不改变已提交状态。
- 前台返回不确定：通过相同 command ID 查询结果，禁止生成重复意见。
- 后台证据失败：逻辑意见保持已保存，发布状态明确为 pending／blocked；Agent 不读半成品。
- 重启后：过期作业租约重新排队，临时 UI 草稿按现有恢复边界处理。
- 删除和几何替换走同一增量路径，不能触发全页加载闪烁。

## 12. 组件职责与预期代码边界

### 12.1 UI

- `AnnotationToolbar`：固定“标记”按钮、菜单、快捷键和只读呈现。
- `AnnotationToolMenu`：工具列表与 roving focus；不持有评审数据。
- `annotationToolRegistry`：编译期工具元数据和手势策略入口。
- `annotationModel`：拆分 `activeTool` 与编辑阶段，维护草稿状态转换。
- `annotationGeometry`：点、箭头、椭圆的纯几何、约束和命中函数。
- `AnnotationCanvas`：统一 Pointer 生命周期和可交互手柄，不解释持久化协议。
- `annotationScene`：全部图片 Anchor 的确定性只读绘制与编号锚点。
- `ImageReviewWorkbench`：把 UI 意图交给现有 Review 协调器并应用最小 Patch。
- `ImageMagnifier`／`ImagePreviewSurface`：继续只接收通用 Painter，不依赖 Review DTO。

### 12.2 Rust Domain、Application 与 Infrastructure

- Domain：新增显式值对象和枚举分支，集中合法性约束。
- Application：继续接收领域 Anchor，不处理屏幕坐标和样式。
- Tauri DTO：双向穷尽映射新分支，拒绝未知与非法数据。
- Authoring codec/store：序列化完整逻辑状态，保持事务、幂等和大小边界。
- v4 protocol：严格 Schema、编解码、历史和读取结果。
- Evidence renderer：新增三种形状与确定编号位置。
- Native reader：识别 v3/v4，保持发布头和源完整性门禁。

不得让 React 组件直接写文件，不得让 Domain 导入 Canvas／Tauri，不得让通用图片预览依赖
Feedback DTO，也不得让证据渲染器依据 UI DOM 截图生成权威数据。

## 13. 可访问性与视觉约束

- 标记菜单使用语义化 menu／menuitemradio 或等价的可访问模式；支持方向键、Enter、Space、
  Escape，并在关闭后把焦点还给“标记”按钮。
- 每项同时显示名称和快捷键，不只依赖图标。
- 工具图标复用项目现有图标体系；不使用文字字符、emoji 或临时 CSS 图形代替正式图标。
- 标记选择不能只依赖颜色；使用编号、选中轮廓和可读名称共同表达。
- 点与箭头端点提供至少 24 × 24 CSS px 的命中区域，视觉尺寸可以更小。
- 高缩放、窄窗口、意见栏开关和系统缩放下，菜单、输入框和手柄不得超出可操作区域。
- 既有高对比标记色、按钮圆角、间距、字体层级和焦点环保持一致，不另起视觉系统。

## 14. 测试与验收

### 14.1 纯逻辑与 Domain

- 点边界、非有限数、越界数据；
- 箭头相同端点、越界端点、方向保持；
- 椭圆正宽高、边界、Shift 圆形约束与不同源图比例；
- 所有新 Anchor 的 DTO、Domain、authoring codec 和 v4 协议往返；
- v3 → v4 无损读取，v3 不被改写；
- JSON Schema 严格拒绝未知 kind、未知字段和非法数值；
- 更新几何保留 Feedback ID，并产生正确目标修订。

### 14.2 UI 交互

- “标记”按钮固定、菜单排序、当前选中项、点击外部和键盘焦点恢复；
- `P/A/B/R/O/V`、Space、Shift、Esc 和输入框快捷键隔离；
- 点单击、箭头方向拖拽、椭圆拖拽与圆形约束；
- 保存后工具保持激活；
- 标记与意见栏双向选择；
- 点拖动、箭头双端点、矩形／椭圆移动缩放、画笔重绘；
- 缩放、平移、旋转、窗口调整和意见栏开关后，绘制及命中仍准确；
- 保存、取消和编辑按钮在任意视口变换后可点击；
- 切图与返回网格的未保存保护。

### 14.3 渲染与证据

- 舞台与放大镜对五种局部 Anchor 的投影一致；
- 放大镜中显示保存标记和临时几何，不复制手柄／编辑器；
- 0°、90°、180°、270° 与不同图像比例下保持重合；
- 高 DPI Canvas、线宽限制、编号可读性和边缘避让；
- 原生证据与 v4 Anchor 方向、区域和编号一致；
- 原图摘要在评审前后不变。

### 14.4 保存、发布与回归

- 保存只应用最小 Patch，不触发整页 loading、图片重新解码或视口重置；
- 快速连续修改不会发生旧写覆盖新写；
- command ID 重试不重复 Feedback；
- 发布 pending／blocked 时 Agent 读取受门禁；
- 前台保存延迟继续满足既有预算；
- 画笔、矩形、整图意见、编辑、删除、存档、历史、放大镜、网格和视频预览全部回归；
- 运行 UI、Rust、协议、架构边界、构建和全量质量门禁。

## 15. 实施顺序

1. 先以失败测试冻结新 Anchor 语义、v4 Schema 和 v3 兼容边界。
2. 扩展 Domain、DTO、authoring codec、协议和原生读取器。
3. 扩展原生证据渲染，确保 Agent 数据与证据先形成端到端闭环。
4. 重构 UI 工具状态与注册表，再实现点、箭头、椭圆几何和编辑。
5. 将五种局部 Anchor 接入共享场景与复合放大镜。
6. 实现统一标记菜单、快捷键、焦点和边缘适配。
7. 验证增量保存、发布门禁、失败恢复和性能预算。
8. 更新产品说明、快捷键、协议文档、Schema 和验证报告。
9. 使用真实测试工程执行桌面交互验收，再运行全量回归。

## 16. 完成标准

只有同时满足以下条件才算完成：

- 用户可从统一“标记”菜单稳定创建、保存、编辑和删除五种局部标记；
- 点、箭头和椭圆在任何受支持视口变换下定位准确；
- 保存无整页闪跳，正常延迟符合既有预算；
- 放大镜、画布、原生证据和 Agent JSON 对每个 Anchor 给出一致语义；
- 旧 v3 数据保持可读、不可变，新 v4 数据通过严格 Schema 与原生读取器验证；
- Agent 不能读到草稿、半发布数据或过期状态；
- 旧功能与架构边界全量回归通过；
- 产品与协议文档明确记录功能和开发初期的交付边界。
