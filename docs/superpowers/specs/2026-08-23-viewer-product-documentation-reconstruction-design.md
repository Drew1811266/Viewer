# Viewer 0.1.6 产品文档重建设计

## 1. 背景

Viewer 已进入 `0.1.6` 持续开发阶段，但现有文档体系主要服务于需求规划、架构决策和阶段验收，尚未形成一套以当前软件实际行为为准的软件产品文档。现有 `docs/PRODUCT_SPEC.md` 同时包含目标需求与已实现行为，`docs/README.md` 又将大量阶段性设计稿标记为 Active，容易让用户和开发人员将规划误认为已经交付的功能。根目录 `README.md` 仍将当前版本写为 `0.1.5`，也说明当前缺少可靠的版本一致性维护机制。

本次重建以 Git 标签 `v0.1.6`、提交 `4f1e839763ba8cef143701bd393f023e445baad6` 对应的软件实际代码为基线，建立面向使用者、产品维护者和开发者的分层产品文档。项目仍是开发版，不纳入签名、公证、商店发布或正式销售流程。

## 2. 目标

1. 让读者无需阅读源代码即可理解 Viewer 0.1.6 是什么、适合什么工作、已经能做什么，以及不能做什么。
2. 提供从打开项目到浏览、搜索、审阅、预览、对比、整理和退出项目的完整操作说明。
3. 集中记录快捷键、支持格式、数据存储、隐私边界、缓存、权限和常见故障处理。
4. 明确区分当前产品事实、历史设计、未来规划和一次性验收证据。
5. 建立后续版本可持续更新的产品文档入口和版本记录。
6. 消除根 README、产品规格、文档索引之间的版本与能力描述冲突。

## 3. 非目标

本次工作不包含：

- 新增、修改或修复 Viewer 功能；
- 改变播放器、图片预览、搜索、文件操作或其他界面设计；
- 建设面向公开发售的安装、签名、公证、自动更新或商店发布文档；
- 将历史设计稿改写成当前功能；
- 删除历史规格、实施计划、验收记录或架构决策；
- 承诺代码和测试尚未证明的兼容性、性能或产品能力。

## 4. 读者与使用场景

### 4.1 软件使用者

需要知道如何启动开发版、选择本地项目、理解界面、完成素材审阅和安全文件整理，并在权限、预览或视频播放失败时自行恢复。

### 4.2 产品维护者

需要有一份当前版本的功能边界和已知限制，能够在功能调整后定位必须同步更新的文档。

### 4.3 开发与测试人员

需要从产品行为说明追溯到实际代码、测试和配置，同时仍可通过现有架构、ADR、质量和验收文档了解实现细节。

## 5. 事实来源与判定规则

### 5.1 事实来源优先级

出现冲突时，按以下顺序认定 0.1.6 的实际行为：

1. `v0.1.6` 对应的运行代码、类型定义和用户界面；
2. UI 单元/交互测试、Rust 单元/集成测试和原生验收测试；
3. `Cargo.toml`、`Cargo.lock`、`src-tauri/tauri.conf.json`、运行时锁文件和安全配置；
4. 已完成的验收记录和架构决策；
5. 现有产品规格、设计稿和实施计划。

低优先级材料与高优先级证据冲突时，以高优先级证据为准，并在必要时将差异记录为历史规划或当前限制。

### 5.2 功能状态

产品文档只使用以下状态：

- **当前可用**：代码存在，并有测试或可直接追溯的运行路径支持；
- **部分可用**：主要路径存在，但存在明确的格式、状态、平台或交互限制；
- **当前不提供**：代码中没有对应入口，或现有实现明确拒绝该能力；
- **开发限制**：功能可用，但仅在当前开发环境、目标平台或开发启动方式下验证。

“计划”“应当”“未来支持”等内容不得出现在当前能力陈述中。确需保留时，只能放入历史或路线图文档，且不得由产品文档索引标记为当前事实。

### 5.3 证据记录

正文以用户可理解的语言描述行为，不在每一段堆叠源代码路径。`FEATURE_REFERENCE.md` 在每个主要功能域末尾记录紧凑的证据入口，便于维护者复核。证据入口至少包含负责该功能的前端组件、IPC 命令或关键集成测试之一。

## 6. 信息架构

### 6.1 权威产品规格

重写 `docs/PRODUCT_SPEC.md`，使其成为 Viewer 当前开发版的产品基线，包含：

- 文档适用版本和事实日期；
- 产品定位、目标用户和使用边界；
- 运行平台与开发版状态；
- 核心信息架构和端到端工作流；
- 功能域摘要；
- 数据、隐私和安全原则；
- 当前限制；
- 配套产品文档入口。

该文件不再承载未来需求清单。历史需求仍保留在 Git 历史和现有阶段性设计文档中。

### 6.2 产品文档目录

新增 `docs/product/`，包含以下文件：

| 文件 | 单一职责 |
| --- | --- |
| `README.md` | 产品文档入口、适用版本、阅读路径和文档状态说明 |
| `USER_GUIDE.md` | 面向使用者的完整操作流程 |
| `FEATURE_REFERENCE.md` | 各功能域的详细行为、状态、边界和证据入口 |
| `SHORTCUTS.md` | 键盘、鼠标、触控板操作和焦点冲突规则 |
| `SUPPORTED_FORMATS.md` | 图片、文本、视频候选格式、实际预览能力和限制 |
| `DATA_PRIVACY.md` | 项目数据、`.viewer` 元数据、索引、缓存、网络与隐私边界 |
| `TROUBLESHOOTING.md` | 项目、权限、扫描、图片、文本、视频和文件操作故障处理 |
| `DOCUMENTATION_MAINTENANCE.md` | 版本升级时的事实复核和文档同步清单 |

### 6.3 版本记录

新增根目录 `CHANGELOG.md`，采用按版本记录的开发变更日志。首个整理版本为 `0.1.6`，只概括仓库历史能够证明的主要新增、调整和修复，不伪造更早版本的完整发布记录，也不将开发标签描述成已公开发布的软件包。

### 6.4 仓库入口与索引

- 更新根目录 `README.md` 至 `0.1.6`，保留开发者快速开始与架构入口，并增加产品文档和变更日志链接。
- 重构 `docs/README.md`，优先展示当前产品文档、工程文档和历史资料三个层级。
- 阶段性设计稿、实施计划、评审和进度记录统一标记为历史或时点证据；只有当前产品基线、当前技术基础和仍生效的 ADR 可列为当前来源。

## 7. 内容边界

### 7.1 必须覆盖的实际功能域

正文必须依据 0.1.6 代码逐项核对并覆盖：

- 空项目入口、文件夹选择和文件夹拖入；
- 单窗口、单项目会话和关闭/重新选择项目；
- 渐进扫描、目录树、内容文件夹概览和聚合浏览；
- 图片、文本、视频与其他文件的分类展示；
- 五档缩略图密度和渐进缩略图加载；
- 搜索、范围、筛选、排序、分页和文本片段；
- 单选、多选、范围选择、框选和全选行为；
- 保留/待定/淘汰、收藏和清除审阅状态；
- 图片适应窗口、缩放、平移、旋转、切换和放大镜；
- Markdown/TXT 双栏文本预览、编码切换、截断提示和链接处理；
- 多图对比、同步/独立查看、原图请求队列和对比数量边界；
- 视频卡片、封面、原生视频预览、播放控制、时间轴、逐帧、音量、速度、全屏、重播和视频缓存；
- 重命名、批量重命名、复制、移动、移入废纸篓、Finder 拖出和会话撤销；
- 操作预检、冲突处理、进度、取消、结果和恢复；
- 外部文件变化、上下文修复和文件监听；
- 只读项目、权限恢复、异常文件和安全错误提示；
- 设置项、数据存放、缓存上限和清理行为；
- 当前平台、开发启动、网络和安全边界。

### 7.2 必须明确的限制

文档必须明确而不是弱化以下类型的限制：

- 当前只验证 Apple Silicon 和 macOS 13 或更高版本；
- 当前是源码构建和开发使用阶段，没有公开安装包承诺；
- 一次只打开一个本地项目；
- Viewer 不是图片编辑器、文本编辑器、视频编辑器或云端素材管理系统；
- 不提供账户、云同步、遥测、自动上传和应用内网页浏览；
- 具体格式支持以代码分类与打包媒体运行时实际能力为准；扩展名被识别不等于内容一定能够解码；
- 文件系统权限、损坏文件、外部变化和媒体解码失败可能限制单项操作，但不应被描述成全局功能失效；
- 撤销只覆盖代码实际记录的安全操作和当前项目会话，不作无限历史承诺。

## 8. 编写原则

1. 使用简体中文，首次出现的技术名称可保留英文。
2. 先说明用户看到的结果，再解释条件、限制和恢复方法。
3. 统一使用界面中的真实中文文案，不为不存在的按钮或菜单命名。
4. 操作步骤必须包含入口、前置条件、预期结果和失败时的恢复方式。
5. 支持格式必须区分“扫描候选”“可生成预览”“依赖媒体内容解码”三种概念。
6. 安全文件操作必须说明移动、复制、废纸篓和撤销的不同语义。
7. 所有绝对性描述都必须能被代码、测试或配置直接证明。
8. 同一事实只设一个详细来源；其他文档通过链接引用，避免复制后漂移。

## 9. 验证策略

文档完成后执行以下验证：

1. 版本扫描：当前文档不得继续把 `0.1.5` 描述为当前版本。
2. 占位符扫描：不得存在未完成标记、模糊的后补承诺或未经解释的空章节。
3. Markdown 相对链接检查：本次新增和修改文档中的本地链接必须指向存在的文件。
4. 功能清单复核：第 7.1 节每个功能域都必须映射到产品规格、用户指南或功能参考。
5. 事实抽查：支持格式、快捷键、设置、视频控制、文件操作和只读边界分别与代码及测试交叉核对。
6. 仓库门禁：运行 `pnpm test:policy`，确认文档变更没有破坏仓库策略；如文档重建涉及策略测试，则运行完整 `pnpm verify`。
7. 差异检查：运行 `git diff --check`，确认没有空白错误，并人工查看最终文件清单。

## 10. 完成标准

只有同时满足以下条件，才可认为 Viewer 0.1.6 产品文档重建完成：

- 第 6 节列出的文件全部存在并具有明确职责；
- `docs/PRODUCT_SPEC.md` 不再混入无法由 0.1.6 证明的未来需求；
- 使用者能够仅通过产品文档完成主要工作流并理解常见错误；
- 支持格式、快捷键、数据与隐私、故障排除均有独立可检索入口；
- `README.md`、`docs/README.md`、产品规格和变更日志的版本与状态一致；
- 历史资料仍被保留，但不会被标记为当前产品行为来源；
- 验证策略全部执行并记录结果。
