# 从 Houdini 与 OpenUSD 反推：生成计划到底是什么

## 1. 两种世界观

### 1.1 Houdini：作品是程序，画面是采样

Houdini 里艺术家做的不是一张图，而是一台**能产出这一类图的机器**。`.hip` 是程序；
视口里的画面是一次 **cook**——程序在当前参数下的一个采样。

这条信念推出了一连串我们今天熟悉的设计：

- **参数是真正的设计面。** 改参数便宜，重新 cook 即可；所以创作是"在参数空间里游走"，不是"改像素"。
- **cook 是按需的、增量的。** 只有脏了才重算，脏可以沿着依赖往下传。所以系统必须知道自己依赖什么。
- **节点是小而确定的变换。** 一个节点一件事，组合出复杂行为；而不是一个大节点做全部。
- **网络是可读的文档。** 别人看你的节点图，能读懂你的意图。所以命名、封装（HDA）、布局都是工作的一部分。
- **结果可丢弃。** 没人备份视口截图，大家备份 `.hip`。

PDG/TOPs 把同一套信念搬到了"任务"上：work item 是任务的最小单位，属性顺着依赖流下去，
wedge 用属性取值展开变体，partition 归并。官方文档里那句"静态 work item 优先于动态"不是风格
偏好，而是这条信念的直接推论——**能事先看见工作量，才谈得上调度和估算**。

### 1.2 OpenUSD：场景是共识，真相是计算出来的

USD 里没有一个文件"就是"场景。舞台（stage）是许多层、许多作者、许多时间点的意见（opinion）
**解析**出来的结果。没有任何一方拥有"最终值"。

它的设计选择同样是这条信念的推论：

- **组合弧是分类型的。** reference、payload、inherits、variant、specialize 不是同一种"链接"，
  它们对身份、加载时机、覆盖语义各不相同。**关系的种类本身携带语义。**
- **稀疏是默认。** 你只写与来源不同的部分；其余靠引用继承。
- **强弱的差别是结构性的。** 弱意见不是被丢弃，而是在强意见缺席时生效。
- **扁平化是显式动作。** 作者态是组合，交付态是拍平；两者不能混。
- **命名空间是身份，而且可以迁移。** 重命名不要求删掉重来，而是记一条 relocate，引用继续解析。

### 1.3 两者共享的隐藏前提

这是我认为最值得抄的一点，而且它不是任何一项功能：

> **昂贵的产物是可丢弃、可重建的；便宜的结构才是资产。**

Houdini 丢掉画面，保住 `.hip`；USD 丢掉渲染结果，保住层。它们都服务于同一个经济学：
**再生成很贵，但重新表达很贵得多。**

## 2. 我们的领域有一处比它们更难

Houdini 的艺术家会看最终渲染；USD 的评审者会看镜头。**他们假设评审者能看全集。**

我们的用户不能。50 张图，注意力只够看十几张。用户的判断是**抽样**，不是全量。
这是它们都没有处理的问题。

所以真正的命题不是"把计划画得好看"，而是：

> **让 12 张样本足以判断一个 50 张的程序，并且让判断能精确地改回去。**

这句话推出四个能力，缺一不可：

| 能力 | 问题 | 对应机制 |
| --- | --- | --- |
| 代表性 | 我抽的 12 张能代表剩下 38 张吗？ | 计划必须暴露它的轴，抽样要能按轴覆盖 |
| 定位 | 这张错了，是程序里哪一句错了？ | 来源追溯（片段 → 提示词 → 分镜） |
| 最小修正 | 改这一处，该动的是不是只有这一类？ | 影响面计算 |
| 修正验证 | 它真的只改了我说的那处吗？ | 声明意图 vs 实际 diff |

前三条我们已经在讨论；第四条没人提过，见 §5。

## 3. 七个可迁移的抽象

下面七条不是功能，是**判断问题的角度**。

### A1. 程序与样本分离

计划是资产，图片是采样。推论：

- 计划 revision 不可变；图片永远属于某个 revision，而不是"属于项目"。
- 聊天记录不是资产——**它是程序的草稿**。程序只有落进计划文件才算数。
- 由此也解释了为什么"直接改图"永远不该进 Viewer：那会把资产降级成样本。

### A2. 参数变更 ≠ 拓扑变更

Houdini 里改参数会 recook 下游，但节点还是那个节点；改拓扑（增删节点、改连接）才会让身份断裂。

这条区分直接解决了我们的一个悬而未决的问题：**标记什么时候该自动关闭？**

| 变更类型 | 例子 | 对标记的影响 |
| --- | --- | --- |
| 参数变更 | 场景片段改措辞、分镜 delta 改写 | 同一张图的意图变了 → 标记可以判为"已处理" |
| 拓扑变更 | 分镜换了所属场景、新增/删除分镜、改名 | 这张图还是不是原来那张图，存疑 → 标记**不能**自动关闭，必须显式解析 |

今天我们的规则是"内容哈希变了就算已改动"，这是把两种变更混为一谈。**参数变更是"改了"，
拓扑变更是"换了"。** 混淆的后果是：Agent 把一张图挪到别的组，用户之前的意见被静默关掉。

### A3. 脏是状态，不是事件

Houdini 的脏标记是**持续状态**，不是一次通知。我们现在的"本次改动影响 12 张"是一次性事件——
刷新一下就没了。

状态化的版本是：每个分镜相对当前计划都有一个持久状态：

```
未生成  →  已生成（与计划一致）  →  已生成（计划已变，待重生成）
                    ↓
             已评审：通过 / 待改
```

这比"影响面"更有用，因为它可以随时查询、可以排序、可以当作工作队列：
**"这版里还有 12 张是旧的"** 比 **"刚才改了 12 张"** 有价值得多。

### A4. 稀疏表达，以及"重复即缺节点"

USD 的默认是只写差异。我们的维度值承担共性，分镜只写 delta——已经这么做了。

但还可以再进一步：**如果一个句子在 10 个分镜里重复出现，那说明缺一个值节点。**
Houdini 的网络里，重复的节点簇会被封装成 HDA；我们的计划里，重复的片段应该被提成维度值。
这条可以做成校验建议（Viewer 提示而非阻断）：重复率高 → "这段描述出现在 12 个分镜里，
是否提成一个共享值？"

### A5. 关系要分类型

USD 的组合弧分类型，因为它们语义不同。我们今天的边只有一种"引用"，这会导致：

- 分镜 A 用值 X（使用）
- 值 X 派生自值 Y（继承）
- 分镜 A 与 B 属于同一组（归组）
- 分镜 A 必须在 B 之后生成（依赖）

这四种关系在身份、传播、失效、UI 上的行为完全不同，却会被画成同样的线。**边必须带类型**，
且每种类型要定义它传播什么（传播片段？传播脏？传播标记？）。

### A6. 组合与扁平化分离

作者态是组合，交付态是拍平。我们已经定了（文件存组合，读取器输出拼好的）。

补充一条：**扁平化必须是显式、可复现、带版本的。** 读取器输出的每个分镜应当带
`composedFrom`（用了哪几个值的哪个版本），否则外部工具拿到一条 prompt 却不知道它从哪来。

### A7. 命名空间可以移动，但必须记录

USD 支持 relocate：重命名不破坏引用。我们之前定的规则是"id 只能加不能改"——这对 Agent 太苛刻，
现实里它一定会改名（`s1` → `s01`、`夏装` → `夏季`）。

更好的规则：**允许改，但必须在 revision 里声明 `relocations`**。Viewer 据此把旧标记迁移到新 id，
并把它标记为"目标已改名"而不是"目标已消失"。没有声明的改动仍然按"删除 + 新增"处理——
这样既给了自由，又保住了可追溯性。

## 4. 落到协议与界面的改动

| 抽象 | 协议 | 界面 |
| --- | --- | --- |
| A2 | revision 内区分 `parameterChanges` / `topologyChanges`（派生） | 标记状态从三态改为四态：待处理 / 已改 / **已换** / 已失效 |
| A3 | 分镜状态由 Viewer 派生，可查询 | 清单增加"状态"列与筛选：还有多少张是旧的 |
| A5 | 边带 `kind`：`uses` / `derives` / `belongs` / `depends` | 不同边不同画法，图例说明 |
| A6 | 读取器输出 `composedFrom` + `shotHash` | 详情里显示拼装来源 |
| A7 | `relocations: [{kind, from, to}]` | 改名后标记显示"目标已改名"并可继续 |
| A4 | 校验建议（非阻断） | 重复片段提示"是否提成共享值" |

## 5. 一个新东西：声明意图 vs 实际 diff

这是从它们的"世界"里推出来、但它们自己没做的事。

Agent 每发一版，都可以附一句**它认为自己改了什么**（不是给用户看的说明，是给系统校验的声明）：

```json
"changeNote": {
  "intent": "把夏天的场景从棚内改成海边，其余不动",
  "claims": [
    { "kind": "shot", "id": "s01", "field": "scene", "from": "studio", "to": "beach" },
    { "kind": "shot", "id": "s02", "field": "scene", "from": "studio", "to": "beach" }
  ]
}
```

Viewer 算出**实际 diff**，然后三样东西并排：

- 它说要改的，实际改了 → 一致
- 实际改了但没说 → **越权**（用户没要求的地方被动过）
- 说了但没改 → **漏做**

为什么这很重要？因为用户只抽样 12 张。如果 Agent 顺手改了三张他没看的图，用户永远发现不了。
**声明意图让"没看的部分"也被审计。** 这正是抽样验证能成立的前提——抽样之所以危险，是因为
未抽样的部分无人看管；而"声明 vs 实际"给未抽样的部分加了一道自动检查。

这条不是抄来的。它是把 Houdini 的"依赖可追踪"和 USD 的"意见可解析"拧在一起，用在我们这个
"用户只能看一部分"的场景上，得到的唯一合理结论。

## 6. 与我们的世界观不兼容的做法

这不是"不抄"，是"它们的解法在它们的约束下成立，在我們的约束下不成立"。

- **自由 DAG。** Houdini 能承受，是因为有大量受训的艺术家、成套节点库、和"网络即文档"的行业纪律。
  我们的作者是 LLM、读者是设计师、审阅是抽样。自由 DAG 会同时失去可读性和可校验性。
  所以我们保留**受控词汇**（值 / 分镜 / 组 + 四种带类型的边），而不是通用图。
- **多层意见强度（LIVRPS）。** USD 需要它，因为有几十个部门在同一个镜头上叠加。我们只有两个作者
  （Agent 写计划、用户写标记），没有冲突可解。全套分层是给不存在的协作付费。
- **可执行表达式（VEX）。** Houdini 的规则是代码，因为求解器要跑它。我们的规则是自然语言，
  因为要读懂它的是 Agent。把规则变成可执行程序，会让"意图"重新变成"实现"，失去可读性。
- **调度与农场。** 我们不执行。执行在 Agent 那边。我们只需要知道"哪些还没做"。

## 7. 结论

两个系统教给我们的不是结构，而是三条信念：

1. **贵的产物可以扔，便宜的结构才是资产。**
2. **关系要有类型，否则等于没有关系。**
3. **能算出来的真相不要写下来；写下来的真相会骗人。**

我们的领域多了一条它们没有的约束：**判断只能靠抽样。** 于是产品的核心问题变成：

> 如何让一次稀疏的人眼判断，变成对程序的精确、最小、可验证的修正。

这个问题的答案，就是我们接下来要设计的东西。
