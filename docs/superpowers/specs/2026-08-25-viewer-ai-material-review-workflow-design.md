# Viewer AI 素材评审闭环产品方向与架构设计

> Status: Active
>
> 日期：2026-08-25
>
> 类型：未来产品方向与架构设计
>
> 当前事实边界：本文定义已经确认的未来方向，不表示 Viewer 0.1.6 已实现这些能力；
> 当前产品行为仍以 [`PRODUCT_SPEC.md`](../../PRODUCT_SPEC.md) 为准。

## 1. 背景与产品定位

Viewer 0.1.6 已经具备本地图片、文本和视频的批量浏览、预览、比较、标记与轻量整理
基础。未来产品目标不是继续扩展成通用媒体浏览器，而是成为 AI 素材生产工具链中的
高效人工评审环节。

目标工作流是：

```text
AI Agent 创建生产任务
  → 图片或视频工具批量生成素材
  → Viewer 接收生成结果并进行人工评审
  → Viewer 发布机器可读的返工意见
  → 外部 Agent 读取意见并生成新版本
  → Viewer 关联新旧版本并进入下一轮复审
```

Codex、Claude、OpenCode 或其他 AI Agent 都只是可能的外部执行端。Viewer 的领域模型、
存储协议和评审流程不得依赖任一具体 Agent、模型供应商或生成工具。

产品的核心价值是把人的审美判断和修改意见可靠地关联到具体生产任务、素材版本与内容
位置，使外部 Agent 能在不猜测文件和评审状态的前提下继续返工。用户不需要把意见写成
机器式结构；自然语言原文是意见的权威内容，Viewer 只负责自动维护必要上下文。

## 2. 已确认的产品原则

1. **Viewer 只负责评审闭环。** Viewer 不启动 Agent、不调用模型、不管理生成任务执行过程；
   外部 Agent 主动读取已经完成的评审记录。
2. **项目文件是事实来源。** 评审记录保存在项目内的 `.viewer/reviews/`，不以本机数据库、
   某个 Agent 或连接器作为唯一事实来源。
3. **生产任务清单可选。** 有清单时建立任务、批次和版本关系；没有清单时，普通文件夹
   仍可直接进入评审。
4. **用户使用自然语言。** Viewer 不要求用户填写结构化问题分类、返工参数或逐项通过表单。
5. **评审采用例外驱动。** 用户只给需要返工的素材留下意见；完成本轮后，其余可评审素材
   默认通过。
6. **完成动作是唯一判断边界。** 出现在网格中、停留一段时间或进入大图都不等于已经评审；
   用户主动完成本轮才发布结果。
7. **本轮素材名单固定。** 评审开始后新增的文件不自动进入本轮，也不会被误判为通过。
8. **一条意见可以作用于多个目标。** 用户可以对一个或多个素材写一条共同意见。
9. **精确标注属于长期核心能力。** 意见可以定位到图片区域，以及视频时间点或时间段；
   定位信息不取代自然语言。
10. **返工版本必须可追溯。** 新版本与原素材、原意见和生成轮次保持关系，并支持对照复审。
11. **历史只追加、不覆盖。** 每轮完成结果形成独立快照；外部 Agent 默认读取最新完成轮次，
    同时可以追溯完整历史。
12. **手动和自动交接并存。** 用户可手动打开文件夹，Agent 也可通过开放命令把项目路径交给
    Viewer；两种入口调用同一应用用例。
13. **文件协议是架构主干。** CLI、MCP、本地 API 或 Agent 插件只能作为适配器，不能建立
    平行的评审事实来源。

## 3. 目标、非目标与阶段边界

### 3.1 目标

- 在大量图片和视频中，只对异常素材留下返工意见，避免逐项确认通过。
- 让自然语言意见精确关联任务、批次、素材版本、图片区域或视频时间范围。
- 为外部 Agent 提供稳定、公开、版本化且可独立读取的完成结果。
- 支持多轮返工、版本对照和历史追溯，不因文件改名或替换造成意见错配。
- 保持本地优先、项目可迁移和 Agent 无关。
- 让手动文件夹工作流在没有任何 Agent 集成时仍然完整可用。

评审轮次的正式目标是图片和视频 Asset Version。项目中的文本和其他文件可以继续作为
上下文浏览，但除非未来经过独立设计扩展协议，否则不进入本轮 Outcome，也不会因没有意见
而被自动判定为通过。

### 3.2 非目标

- 在 Viewer 内运行 Agent、模型、提示词编排或生成工具；
- 让 Viewer 自动理解、重写或总结用户的自然语言判断；
- 为每个 Agent 建立一套独立的核心数据模型；
- 强制用户逐个打开素材、逐项点击“通过”或填写结构化评审表；
- 通过滚动位置、停留时间、缩略图曝光或大图打开次数推断用户是否完成评审；
- 把 Viewer 扩展为云端协作平台、通用数字资产管理系统或生成任务调度器；
- 在本文中承诺具体实施日期，或把未来设计描述为当前功能；
- 代码签名、Apple 公证、正式安装包、公开发布和发售工作。这些事项不属于当前开发阶段，
  也不是后续各功能阶段的默认完成条件。

## 4. 核心领域模型

### 4.1 Project

用户打开的本地项目根目录，也是素材相对路径、`.viewer` 元数据和评审记录的安全边界。
所有协议路径都相对于 Project，不保存用户机器上的绝对路径。

### 4.2 Production Manifest

由外部生产工具提供的可选只读输入，描述生产任务、批次、素材身份和已知版本关系。
Viewer 不修改原始清单。清单缺失时，Viewer 仍可根据项目目录创建自己的稳定素材身份。

### 4.3 Production Task 与 Batch

Production Task 表示一次业务生产目标；Batch 表示其中一组需要共同评审的输出。二者在
没有生产清单时都可以缺省，不能成为普通文件夹评审的前置条件。

### 4.4 Review Stream

Review Stream 是一组连续返工与复审轮次的稳定内部身份。同一 Project 可以同时包含多个
Task、Batch 或普通文件夹评审，因此不能使用一个项目级“最新轮次”代表所有工作。

有生产清单时，Viewer 根据明确的 Task/Batch 身份建立 Review Stream；没有清单时由 Viewer
创建本地身份。原素材进入返工、产生新版本并继续复审时，后续 Review Round 仍属于同一
Review Stream。该名称不必出现在界面中。

### 4.5 Asset Version

一张图片或一个视频在某次生成或返工中的具体版本。Asset Version 至少包含：

- Viewer 或生产清单提供的稳定身份；
- 项目相对路径；
- 能绑定具体内容版本的文件身份或内容指纹；
- 素材类型和必要的媒体边界信息；
- 可选的任务、批次与父版本引用。

文件名和相对路径用于发现与展示，但不能单独证明两个时刻的文件是同一内容版本。

### 4.6 Review Round

Review Round 是一次用户可理解的“本轮评审”。创建时冻结成员 Asset Version 列表，之后
新增的素材不自动加入。它具有以下状态：

```text
Draft → Completed
```

- `Draft` 可以持续保存和恢复，但不能被外部 Agent 当作返工指令。
- `Completed` 是不可覆盖的已发布快照；任何更正都通过新的补充轮次表达。

不提供从 `Completed` 回退并原地改写为 `Draft` 的状态转换。

每个 Review Round 必须属于一个 Review Stream。

### 4.7 Feedback

Feedback 保存用户自然语言原文和一个或多个目标。写下意见即表示对应目标需要返工，
用户不需要再选择问题分类或填写返工参数。

一个 Feedback 可以作用于：

- 一个完整 Asset Version；
- 多个 Asset Version；
- 一个或多个图片区域；
- 一个或多个视频时间点或时间段。

系统可以保存创建时间、作者来源和目标锚点等结构化上下文，但不得用派生文本替换用户原文。

### 4.8 Anchor

Anchor 只负责把 Feedback 定位到具体内容：

- `asset`：整个素材；
- `imageRegion`：相对于已校正显示方向的归一化图片坐标；
- `videoPoint`：相对于绑定视频版本的时间点；
- `videoRange`：相对于绑定视频版本的起止时间。

Anchor 必须绑定确切 Asset Version。原素材发生内容替换后，旧 Anchor 不得自动迁移到新版本；
对新版本的复审需要显式建立新锚点。

### 4.9 Review Snapshot 与 Outcome

用户执行“完成本轮评审”后生成 Review Snapshot。系统为冻结名单中的每个 Asset Version
计算一种结果：

- `revise`：至少有一条有效 Feedback 指向该素材；
- `pass`：素材可正常评审，且本轮没有 Feedback；
- `unreviewable`：Viewer 因内容损坏、解码失败或权限问题无法呈现素材。

`pass` 只在 Review Round 完成时产生。Draft 中没有 Feedback 的素材没有任何通过结论。
`unreviewable` 是默认通过规则的系统级例外，不要求用户填写结构化说明。

### 4.10 Revision Relation

Revision Relation 把返工后的 Asset Version 关联到父版本和触发返工的 Feedback。生产清单
可以自动提供关系；没有清单时允许用户手动关联。关系一旦进入已完成历史便不可原地改写。

## 5. 领域不变量

以下规则必须位于领域或应用层，不得只由界面约定：

1. Review Round 创建后，成员列表不可静默增加或替换。
2. Draft 永远不能更新对应 Review Stream 的“最新完成轮次”索引。
3. Completed 快照必须覆盖冻结名单中的每个素材，且每个素材只有一个最终 Outcome。
4. 只有 Completed 快照可以包含 `pass`。
5. 包含有效 Feedback 的素材必须是 `revise`，不能同时是 `pass`。
6. `unreviewable` 素材不能是 `pass`；系统必须提供安全、稳定的失败类别。
7. Feedback 目标必须属于本轮冻结名单，并绑定同一内容版本。
8. Completed 快照只追加、不覆盖；更正通过新轮次表达。
9. 项目外路径、绝对路径、未知素材身份和版本不匹配的目标必须被拒绝。
10. Agent 交接入口与手动入口必须调用同一创建/打开项目用例。
11. 新旧版本关系必须显式来自生产清单或用户操作，不能仅凭文件名相似度自动确认。
12. 写入失败时不能发布部分完成结果，旧的最新完成轮次保持不变。
13. 每个 Review Round 必须属于一个 Review Stream；“最新完成”只能在同一 Stream 内判断。

## 6. 系统边界与组件职责

### 6.1 Ingress Adapters

负责把外部输入转换为统一应用请求：

- 手动选择项目文件夹；
- Agent 调用开放命令交付项目路径；
- 生产任务清单解析。

Ingress Adapter 只做语法验证、路径归一化和 DTO 转换，不承载评审规则。未来 CLI、URL
scheme、MCP 或本地 API 都属于这一层。

### 6.2 Review Application

负责评审用例编排：创建轮次、保存草稿、添加或移除 Feedback、完成轮次、恢复草稿、关联
返工版本和查询历史。它通过窄端口依赖项目存储、素材身份和媒体可呈现性，不直接依赖
Tauri、React 或具体 Agent。

### 6.3 Review Domain

持有第 4、5 节的状态与不变量。领域层不读取文件、不解析 JSON、不调用媒体解码器，也不
知道 Codex、Claude、OpenCode、CLI 或 MCP。

### 6.4 Project Review Repository

将领域对象持久化到 `.viewer/reviews/`，负责 schema 版本、原子发布、历史只追加、写入租约
和崩溃恢复。项目文件是权威来源；本机缓存只能保存可重建派生数据。

### 6.5 Review UI

负责批量浏览、选择、比较、自然语言输入、图片/视频锚点编辑、提交确认和历史展示。UI
只能通过 Review Application 执行状态变化，不直接写 JSON 或推导最终 Outcome。

### 6.6 External Agent

External Agent 位于 Viewer 进程和信任边界之外。它可以：

- 写入可选生产任务清单；
- 通过开放入口把项目交给 Viewer；
- 读取最新 Completed 快照；
- 根据意见生成新素材与版本关系。

Viewer 不负责 Agent 如何解释或执行自然语言意见，也不保证外部 Agent 的生成结果正确。

标准依赖方向为：

```text
手动入口 / CLI / MCP / 本地 API
             ↓
      Review Application
             ↓
        Review Domain

Project Review Repository、素材身份与媒体能力
作为 Application 的端口适配器，不反向进入 Domain。
```

## 7. 开放项目文件协议

### 7.1 协议分离

协议分为两个方向：

- `viewer.production/1`：外部工具写入、Viewer 只读的可选生产任务清单；
- `viewer.review/1`：Viewer 写入、外部工具读取的评审记录。

两者拥有独立 schema。生产清单无效不能污染评审记录；评审记录也不得改写生产工具的输入。

### 7.2 逻辑目录

```text
项目目录/
├─ viewer-production.json              # 可选
└─ .viewer/
   └─ reviews/
      ├─ index.json                    # Stream 与已发布轮次发现入口
      ├─ drafts/
      │  └─ <review-round-id>.json     # 可恢复草稿
      └─ rounds/
         └─ <review-round-id>.json     # 不可覆盖的完成快照
```

`viewer-production.json` 是默认发现位置；开放命令可以显式传入项目内的其他生产清单相对路径。
任何清单都必须经过相同 schema 与项目边界验证。

### 7.3 生产清单最小语义

生产清单可以包含：

- `protocolVersion`；
- `taskId` 与 `batchId`；
- 每个输出的稳定 `assetId`、项目相对路径和媒体类型；
- 可选父版本、生成轮次和非敏感任务上下文；
- 可选生产工具标识。

提示词、模型参数和生成日志不是必填字段。清单不得把凭证、令牌或机器绝对路径作为任务
上下文。未知可选字段可以保留，但 Viewer 不依赖它们建立核心正确性。

### 7.4 完成快照最小语义

每个 Completed 文件至少包含：

- `protocolVersion`、Project、Review Stream 和 Review Round 身份，以及可缺省的 Task、Batch
  身份；
- 本轮创建与完成时间；
- 冻结的 Asset Version 列表；
- 用户自然语言 Feedback 原文及目标 Anchor；
- 每个素材唯一的 `pass`、`revise` 或 `unreviewable` Outcome；
- 已知 Revision Relation；
- 完整性校验信息。

`index.json` 至少列出所有 Review Stream、每个 Stream 的已完成轮次，以及对应的
`latestCompletedRoundId`。Agent 的标准读取流程是：

1. 读取 `.viewer/reviews/index.json`；
2. 根据交接信息中的 `reviewStreamId`，或明确的 Task/Batch 身份，选择目标 Stream；
3. 找到该 Stream 的 `latestCompletedRoundId`；
4. 读取对应 `rounds/<id>.json`；
5. 校验协议版本、Stream 身份和完整性；
6. 忽略 `drafts/` 下所有内容。

如果调用者没有提供足以唯一定位 Stream 的身份，参考读取器必须返回候选列表，不能擅自把
项目中最后写入的轮次当作目标任务结果。

### 7.5 写入与兼容

- 草稿可以更新，但每次写入都必须使用安全替换，不能留下可被误认的截断 JSON。
- 完成时先持久化新的不可覆盖 Round 文件，再原子更新 `index.json`。
- `index.json` 更新失败时，新 Round 可以作为待恢复孤立记录存在，但不能成为最新完成结果。
- 同一 Project 同时只允许一个评审写入者；其他 Viewer 实例只读。
- 不支持的主版本只能只读，禁止以旧 schema 覆盖；兼容的新增字段应被安全忽略或保留。
- 仓库必须提供 JSON Schema、规范样例和通用参考读取器，具体 Agent 适配器不得自行猜测字段。
- 可以生成 Markdown 摘要供人阅读，但 JSON 是唯一机器事实来源。

## 8. 端到端数据流

### 8.1 手动打开

```text
用户选择项目文件夹
  → Viewer 验证项目与可选生产清单
  → 用户从批次、文件夹或选中素材创建本轮评审
  → Viewer 冻结 Asset Version 列表并建立 Draft
```

### 8.2 Agent 自动交接

```text
Agent 完成生产并写入项目文件
  → Agent 调用开放入口并传入项目路径及可选清单路径
  → Ingress Adapter 验证后调用与手动入口相同的打开项目用例
  → Viewer 展示同一评审工作流
```

自动交接只负责唤起或定位项目，不允许 Agent 绕过用户直接完成评审。

### 8.3 例外驱动评审

```text
用户在网格、预览或对比中发现问题
  → 选择一个或多个素材
  → 输入自然语言意见并可选添加内容 Anchor
  → Viewer 持续安全保存 Draft
  → 用户检查返工意见列表
  → 用户主动完成本轮
  → Viewer 计算 Outcome 并原子发布 Completed 快照
```

缩略图曝光、滚动位置、停留时间和大图打开记录都不参与 Outcome 计算。

### 8.4 返工与复审

```text
Agent 读取最新 Completed 快照
  → 只处理 revise 和 unreviewable 结果
  → 写入新 Asset Version 与可选 Revision Relation
  → Viewer 自动或手动关联父版本
  → 用户对照原素材、原意见和新版本
  → 创建下一轮评审并追加历史
```

## 9. 高效评审交互原则

1. 批量网格是正式评审入口，不是进入大图前的临时列表。
2. 正常素材无需操作；问题素材才产生 Feedback。
3. 多选素材可以共享一条自然语言意见。
4. 写下意见即表示需要返工，不要求额外选择“需返工”状态。
5. 大图、视频播放和对比按需使用，不成为完成条件。
6. 图片区域和视频时间 Anchor 只减少定位歧义，不要求用户填写问题分类。
7. 完成前集中展示本轮意见、目标数量和无法呈现素材，方便用户复核。
8. 完成动作需要明确确认本轮固定名单；不展示伪造的“已逐项浏览”进度。
9. Completed 轮次只读展示；遗漏或修正通过补充轮次表达。

## 10. 异常、一致性与恢复

### 10.1 项目不可写

Viewer 可以继续浏览只读项目，但在创建 Review Round 前明确拒绝写入。评审记录不自动改存
到本机数据库，也不在项目重新可写后静默合并来源不明的本地草稿。

### 10.2 生产清单无效

Viewer 不采用半解析清单。用户收到安全、可操作的错误后，可以忽略清单并以普通文件夹模式
评审。清单中的无效任务或版本关系不能进入项目评审事实。

### 10.3 评审期间素材变化

文件被替换、删除、移出项目或内容身份改变时，对应 Asset Version 进入冲突状态。用户必须
明确排除、重新绑定或移入下一轮后才能完成当前结果。Viewer 不使用相同文件名自动确认身份。

### 10.4 无法呈现

素材因损坏、解码失败或权限问题无法呈现时，系统产生 `unreviewable`，并提供稳定、安全的
错误类别。它不进入默认通过集合，也不要求用户编写一条虚构的返工意见。

### 10.5 写入失败与崩溃

- Draft 保存失败时明确显示“未保存”，内存状态不能冒充持久化成功。
- Round 文件或 `index.json` 任一步失败时不得发布半完成结果。
- Viewer 重启后从项目文件恢复有效 Draft，并识别可安全恢复的孤立完成文件。
- 恢复过程只能完成已验证的原子发布或保留旧索引，不能合并两份含糊状态。

### 10.6 并发写入

Project Review Repository 使用项目内身份绑定的写入租约。同一项目只有一个评审写入者；
租约恢复必须验证原进程和项目身份，不能仅根据超时时间删除另一个活跃写入者的锁。

### 10.7 协议版本

不支持的主版本以只读方式打开，并提示需要兼容版本。Viewer 不删除未知字段、不自动降级，
也不为了继续写入而覆盖未来版本记录。

## 11. 安全与隐私边界

- 所有素材和协议路径必须规范化为项目相对路径，并拒绝 `..`、符号链接逃逸和保留路径冲突。
- Asset Version 身份在读取、标注、完成和返工关联时都要重新验证，避免 TOCTOU 错配。
- 生产清单和评审 JSON 都是不可信输入；解析必须有大小、数量、深度和字符串长度上限。
- 自然语言意见按用户数据处理，界面渲染时不得执行其中的 HTML、脚本或远程资源。
- 协议不记录令牌、凭证和不必要的机器绝对路径；诊断信息不得进入 Agent 可读结果。
- Viewer 不因 Agent 集成获得主动网络权限。外部 Agent 对项目文件的读取由用户授予的环境权限
  控制，不扩张 Viewer 自身的信任边界。
- Markdown 摘要不能包含 JSON 中没有授权公开的额外诊断或路径信息。

## 12. 验证策略

### 12.1 协议契约

- 固定 `viewer.production/1` 与 `viewer.review/1` 的 JSON Schema、有效样例和拒绝样例。
- 使用通用参考读取器证明任何 Agent 都能发现并读取最新完成轮次。
- 验证未知主版本只读、兼容新增字段和缺少可选生产清单的行为。

### 12.2 领域规则

- Draft 不能产生 `pass` 或更新对应 Review Stream 的最新完成索引。
- Completed 覆盖冻结名单中的每个素材且 Outcome 唯一。
- 有 Feedback 的素材为 `revise`；无 Feedback 且可呈现的素材为 `pass`；无法呈现为
  `unreviewable`。
- 新增文件不进入已创建轮次；版本冲突不能被静默解析。
- Completed 不可覆盖，更正只能追加新轮次。

### 12.3 持久化与故障注入

- 在草稿写入、Round 发布和索引更新的每个边界注入失败与进程退出。
- 证明 Agent 只能看到旧的完整快照或新的完整快照。
- 验证租约竞争、崩溃恢复、孤立 Round 和磁盘只读行为。
- 验证文件改名、移动、替换、删除和同名文件不会造成 Feedback 错配。

### 12.4 入口与端到端闭环

- 手动入口和 Agent 交接入口产生相同应用请求与 Review Round。
- 覆盖有清单、无清单和无效清单降级三种项目。
- 完整验证第一轮意见、外部参考读取器、新版本关联、第二轮复审和历史追溯。

### 12.5 交互效率

- 用户能在批量网格直接完成评审，不必逐个进入大图。
- 多选素材能共享一条意见，自然语言原文无损保存。
- 完成规则不依赖曝光、停留时间或预览打开次数。
- 图片区域与视频时间 Anchor 发布时绑定确切 Asset Version。

### 12.6 安全

- 拒绝绝对路径、项目逃逸、未知素材、被替换身份和不受支持的协议降级。
- 对清单数量、嵌套深度、文本长度、Anchor 范围和索引规模执行确定性上限。
- 验证用户文本渲染不执行活动内容，错误结果不泄露绝对路径或内部诊断。

核心测试只使用通用参考读取器，不要求安装或登录任何具体 Agent。

## 13. 分阶段演进

### 阶段 1：开放评审协议基础

建立领域对象、Review Stream、状态机、不变量、Project Review Repository、JSON Schema、
样例和参考读取器。
该阶段先证明记录可被安全、独立地生产和消费，不引入具体 Agent SDK。

### 阶段 2：例外驱动的基础评审闭环

实现固定本轮素材、单个/多个素材的自然语言 Feedback、草稿恢复、完成本轮、默认通过和
`unreviewable`。手动入口和开放命令交接共用一个应用用例。

### 阶段 3：返工版本与多轮复审

接入可选生产任务清单，建立 Revision Relation，提供原素材、原意见和新版本的对照复审，
并完成逐轮追加与最新完成结果发现。

### 阶段 4：精确内容标注

实现图片 `imageRegion`、视频 `videoPoint` 和 `videoRange`。Anchor 在领域和协议层预留明确
扩展边界，但用户交互与媒体坐标验证在此阶段独立完成。

### 阶段 5：开放生态适配

在文件协议稳定后增加 CLI、MCP、本地 API 或具体 Agent 插件。所有适配器调用统一应用端口
并读取同一项目协议；适配器失败不能改变 Review Domain 或项目事实。

每个阶段都需要独立设计、实施计划、测试与用户确认。本路线不设置硬期限，也不把签名、公证、
正式安装包、公开发布或发售作为阶段完成条件。

## 14. 架构验收条件

未来实施必须同时满足：

1. 普通文件夹在没有任务清单和 Agent 的情况下仍可完整评审。
2. 任意遵循公开协议的 Agent 都能在 Viewer 不运行时读取目标 Review Stream 的最新
   Completed 快照。
3. 用户只给异常素材写自然语言意见，正常素材无需逐项操作。
4. 完成动作之前不存在隐式通过；完成后 Outcome 覆盖且只覆盖本轮冻结名单。
5. 公开索引和参考读取器永远不返回半写入轮次或 Draft，合规 Agent 不会把 Draft 误认成
   返工指令。
6. 新增、替换、移动或损坏素材不会被静默误判为通过或错误关联意见。
7. 多轮返工保留原素材、原意见、新版本和最终结果的完整关系。
8. 图片区域与视频时间 Anchor 不因显示缩放、旋转或文件替换失去版本边界。
9. 手动入口、CLI、MCP 和未来适配器不复制领域规则或建立第二事实来源。
10. 当前 0.1.6 产品行为与本文未来目标在产品文档中保持明确区分。

## 15. 后续文档边界

本文是跨阶段的产品方向与目标架构，不直接充当阶段 1 的实施计划。开始开发前，需要为
“开放评审协议基础”单独编写可执行计划，明确代码落点、schema 细节、迁移策略和逐步验证
命令；后续阶段分别设计，不能把五个阶段合并成一次高风险改造。
