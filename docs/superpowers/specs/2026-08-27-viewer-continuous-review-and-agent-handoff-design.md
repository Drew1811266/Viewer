## 1. 结论与阅读入口

采用“自动记录保存版本 + 可选返工依据回传 + 用户手动存档”。用户持续编辑自然语言意见，
成功保存后即可供外部 Agent 读取；不再以“完成本轮”作为读取或继续编辑的门槛。

用户的主流程保持为：

1. 外部工具产出一批素材。
2. 在 Viewer 批量浏览，发现问题后进入大图，标记位置并填写意见。
3. 觉得意见充分后，自行通知外部 Agent 读取并返工。
4. 收到返工素材后，在 Viewer 手动存档对应的上一轮意见。
5. 审查新素材，继续记录本轮问题，然后重复上述过程。

存档的主要作用是向读取方区分“上一轮的意见”和“当前仍有效的要求”。存档不证明 Agent
实际采用了这些意见，不证明修改完成，也不证明用户验收通过。

产品规则见第 4–8 节；模块职责、数据一致性和协议兼容见第 9–13 节；验收要求见第 14 节。
已落地的纯规则、协议仓储及应用用例见[实施计划](../plans/2026-08-27-viewer-continuous-review-and-agent-handoff.md)
和[阶段 C 记录](../../reviews/2026-08-27-continuous-review-application-phase-c.md)；对外读取、桌面和 UI 接入仍是拟实施契约。

## 2. 问题、现状与范围

### 2.1 当前实现的可复用部分与限制

现有实现已有稳定 Feedback ID、版本绑定的 Asset Version、图片规范坐标、编号映射、
原生标注预览、写入租约、原子索引提交及严格的外部读取校验。这些能力继续复用。

主要限制不在标注工具，而在生命周期：

- `review_session.rs` 在完成后进入 `CompletedReadOnly`，释放可写会话。
- `read-latest.mjs` 仅返回索引中的最新 Completed；Draft 不是 Agent 指令。
- 当前会话的 `revision` 在恢复后重新初始化，不能充当持久的外部版本标识。
- 标注预览主要在完成时生成，不能满足“先收到覆盖原图的产出，再存档旧意见”的证据要求。
- 固定 Round 名单阻止用户直接评审范围外的另一张图片。

这是一项生命周期、持久化与外部接口的架构调整，不是单纯解除按钮禁用，也不是把
Completed 改名为 Archive。

### 2.2 本轮范围

- 持续编辑与成功保存即可读，动态加入有意见的素材。
- 完整的当前意见、可核对的保存版本、精确增量和按需历史读取。
- 手动整批或部分存档、后补意见保护、撤销及选择性恢复。
- 素材版本核对、旧证据保留、历史意见继续提出。
- Agent 无关的可选使用依据声明、显式导入及核验；无回传时仍可完成全部主流程。
- 新协议、旧数据迁移与对应 UI 状态、自动化和原生回归验证。

保留既有图片画笔、矩形、整图意见和批量共同意见。保留既有视频浏览及可表达的视频
Anchor；本轮不新增视频时间标注界面，也不把图片证据机制冒充视频历史备份。

### 2.3 明确非目标

- 自动启动、通知或调度 Agent；自动确认它已读、已执行或已修复。
- AI 合并、改写、摘要替代用户意见；自动识别语义冲突并替用户选边。
- 多人协作、云同步、账号、企业审批或多 Agent 调度系统。
- 依据文件名或画面相似度自动判定新旧产出的业务关系。
- 全量原始媒体备份、完整历史视频回放、新的像素编辑工具。
- 自动删除已提交评审历史或技术快照的保留策略。

Viewer 仍处于开发初期。代码签名、Apple 公证、正式安装包、上架、公开发布和发售均不属于
本轮任务、验收条件、阻塞项或默认下一步；只有用户单独授权时才进入相应范围。

## 3. 方案取舍

| 方案 | 收益 | 限制与决定 |
| --- | --- | --- |
| 只保留一份可变意见，存档时整体清空 | 操作和存储简单 | 不能区分交接后修改，也不能稳定引用已读取内容；不采用 |
| 强制提交并锁定交接版本 | 交接边界明显 | 增加用户操作、限制继续修改，且仍不能证明 Agent 实际执行；不采用 |
| 持续保存不可变版本，手动建立存档里程碑 | 自由编辑，精确比较，新旧要求分离 | 需要一致性提交和明确的未知状态；采用 |

普通保存产生后台技术版本；只有用户存档才产生可见的存档记录。技术版本不作为一长串
“第 N 轮”占据日常界面。部分素材可能处于不同返工阶段，不用一个项目级轮次替所有素材
宣告进度。

## 4. 核心语义与不变量

| 概念 | 含义 | 不代表 |
| --- | --- | --- |
| 编辑中内容 | 尚未成功提交的文字、几何或恢复草稿 | Agent 当前指令 |
| 保存快照 | 一次成功提交的完整评审状态，内容不可变 | 一次用户存档或 Agent 已读取 |
| 当前有效意见 | 在指定快照中仍有效、且素材条件允许处理的要求 | 已经执行过的任务 |
| 待确认事项 | 保留但不能直接执行的意见或素材问题 | 没有问题、意见已删除 |
| 返工依据声明 | 外部工具声明本次依据哪个快照、哪些素材 | 执行事实认证或质量验收 |
| 存档 | 用户把指定意见版本移入历史 | 已修复、已通过、要求逆向撤销 |
| 历史引用 | 指向旧意见及证据的背景关联 | 自动加入当前要求 |

必须持续满足：

1. 原始自然语言是修改意图的权威；Anchor 和预览辅助定位，不能替代原文。
2. 批量浏览与大图查看都可用于用户判断，不收集浏览次数、停留时间等作为通过条件。
3. 当前无意见只表示没有当前返工要求，不生成项目级“全部通过”，也不自动回退历史。
4. 每次读取固定一个已提交快照；不把两个快照的文字、标记、编号或预览拼接。
5. 文件变化、读取行为、回传声明和存档动作都不能自动推导“问题已解决”。
6. 当前、待确认、历史的角色必须通过数据结构明确表达，不能只依靠展示顺序或提示文案。
7. 编辑、删除、存档、恢复都受精确版本检查约束；失败不丢输入，重试不重复产生意见。
8. Viewer 不改写源素材，不执行意见，不清除外部 Agent 的上下文，也不承诺阻止它重复执行。

## 5. 持续编辑与素材范围

### 5.1 入口和保存

大图预览仍是局部意见的主要入口。用户可以新增、编辑文字、重绘、调整矩形和删除意见；
已存档历史本身保持不可变，但可“继续提出”或恢复为新的当前状态，不以历史只读锁住工作台。

首次成功保存意见时建立人工 Review Stream 的当前状态。后续打开另一张图片，保存其首条
有效意见时加入当前清单，不要求完成或放弃已有评审。只浏览、筛选、滚动或选择素材不会
自动添加反馈、扩大通过范围或触发存档。人工 Stream 仍按项目唯一，不引入并行人工会话。

局部意见必须同时具有非空文字和有效 Anchor。明确的“保存”操作保持现有习惯；本设计的
“自动记录版本”不是按每个按键发布，也不要求用户手动编号。保存状态区分“保存中”、
“已保存，可供读取”和“未保存／保存失败”。

已成功保存但仍需确认素材适用性的内容，显示“已保存，待确认”，不能用“可执行”代替保存
状态。当前最后一条意见被删除或存档后，仍提交一个完整的空当前状态，不移除当前入口。

存档没有自动保存未确认输入的副作用。存在未保存编辑时，先让用户保存、放弃编辑或返回；
不能把半条意见一起存档。正常导航继续保留现有未保存内容保护。

### 5.2 共享意见的部分处理

批量共同意见可以有多个素材目标。一条文字同时指向图 1 和图 2 时，存档图 1 只移出图 1
对应的目标；图 2 的要求继续有效。编辑剩余当前意见不能改写已存档的图 1 文字。

为此需要稳定的目标身份，而非用数组位置标识目标。批量意见的文字与目标关系见第 9 节。
没有剩余当前目标的意见不再显示为当前项，但其历史版本仍可引用。

## 6. 交接、存档与恢复

### 6.1 保存版本不是交接确认

每次成功保存具有持久 `snapshotId`。读取器返回该标识及完整性摘要；读取器保持只读，不
偷偷记录阅读回执，也不创建存档。用户通知 Agent 的时机由用户决定，不新增强制交接按钮。

外部工具可以返回使用依据声明。Viewer 校验项目、Stream、快照、素材范围及引用关系，
展示“Agent 声明使用”；不展示“已核实执行”。用户也可以明确指定已知的依据快照，来源
记为“用户指定”，不得伪装成外部回传。

### 6.2 存档确认

存档先生成基于当前快照的预览，展示涉及素材、意见数量、依据来源、将移入历史的内容和
将保留的后补内容。整批可一次确认，部分返回时可只选择对应素材。系统不能因为某些文件
已更新而预设所有素材均已返工。

有核验通过的依据时，预选该依据声明覆盖的内容；无依据时，由用户确认当前选中意见进入
历史，并标记“手动存档，交接版本未确认”。未知不阻止主流程，也不能被时间戳猜测取代。
用户可以在确认前排除仍想保留的意见。默认范围是当前评审清单，不是整个文件库。

一次存档可包含多个依据组，但每个被选目标必须只有一个明确的归档依据；冲突声明不按
“最新文件”自动裁决。没有声明的部分独立标为未知，不继承其他素材的声明。

### 6.3 精确移出规则

设存档预览基于当前快照 C，已知返工依据是 B。对选中的每个意见目标：

- 归档保存 B 中的文字和目标版本，而不是拿 C 的新内容冒充 B。
- C 中仍是相同文字版本、目标版本的内容，移出当前清单。
- B 之后新增的意见目标不移出。
- B 之后编辑文字、重绘或重新绑定素材的目标保留；如果素材已变化，保留在待确认事项中。
- 用户已删除的目标保持删除；记录 B 的历史内容不能让它复活。
- 同一批量意见的未选目标保持原状态。

无已知依据时，归档证据来自用户确认的 C，但 `usageBasis` 为空，不能声称 C 已被采用。
存档预览后若当前快照发生变化，重新计算并让用户确认变化，不静默扩大移出范围。

同一个存档命令重试返回原结果。对已归档的同一依据和相同目标再次点击，返回“没有新的
可存档内容”，不制造重复记录。无意见、无新归档覆盖的操作不创建空存档。
去重针对仍有效的存档覆盖；已撤销的存档不阻止用户再次明确存档。

### 6.4 示例

| 事件 | 当前状态 | 历史变化 |
| --- | --- | --- |
| 保存“袖口收紧”，产生 B | 该意见有效 | 无存档 |
| Agent 读取 B | 不变，仍可编辑 | 不自动记录已读 |
| 改为“袖口收紧，保留褶皱”，产生 C | 新文字替代旧文字 | B 仍可精确引用 |
| 产出覆盖原图 | 新文字保留，素材适用性待确认 | 不自动存档 |
| 用户按已知依据 B 存档 | 后补的新文字保留待确认 | B 中旧文字进入上一轮历史 |

若没有 B 的使用依据，Viewer 不自动得出最后一行的结论；用户确认哪些当前意见收起，
记录手动存档和依据未知。

### 6.5 误存档与历史继续提出

- 刚存档且后续没有评审变更，可以撤销；撤销通过追加恢复状态实现，不删除或改写存档记录。
- 即使评审状态未变，也重新检查素材；被覆盖或缺失的源文件不能因撤销恢复成可执行状态。
- 已有后续意见时，提供选择性恢复，不整体回滚。相同身份已出现新文字或几何时，展示差异
  供用户确认；未确认的旧版本不进入有效清单，也不覆盖新内容。
- “继续提出”创建新的 Feedback 身份并记录历史来源。原文可复用，但新素材的适用性必须
  确认；局部意见需要确认位置或重新标记，不无条件沿用旧坐标。
- 删除表示撤回当前要求，不表示要求 Agent 撤销它已经做过的修改。

## 7. 素材换版与证据

### 7.1 业务关系与文件事实分开

逻辑素材身份回答“这是哪份素材”；Asset Version 回答“意见针对哪一版内容”；路径只负责
定位文件。内容指纹相同只能证明字节相同，不能在多个重复文件中自动选择业务归属。

- 明确的素材标识、父版本关系且通过核验时，可以建立版本关联，并记录关系来源。
- 同路径覆盖、近似文件名或相似画面只产生候选关系，由用户确认；本轮不新增相似图 AI。
- 确认只是同一文件改名、移动路径且字节内容不变时，可以更新定位，不伪造返工版本。
- 文件身份不清、重复候选、路径越界或读取失败时，不自动合并。
- 未关联的新素材可以独立评审，后续明确关联历史，不阻塞首次写意见。

仅 mtime 变化而内容未变不算返工。mtime 未变也不能证明内容相同。源校验复用安全打开、
身份核对和内容指纹能力；对外执行条件不能只依靠文件监视通知。

### 7.2 更新后保留但隔离旧意见

检测到内容变化时，旧意见仍绑定旧 Asset Version，不迁移坐标、不自动清空、不判通过。
用户仍可编辑文字、查看证据或存档。编辑旧版本意见不自动确认它适用于新素材。

当前返回结果将不满足源版本条件的目标列为待确认；其他未受影响素材仍可评审和读取。
确认新旧业务关系与确认某条意见适用于新图是两个动作，可以在一个界面完成，但不能
因为确认了版本关系就默认所有旧问题仍然存在。

### 7.3 证据必须早于覆盖风险

首次提交一份图片版本的有效意见前，保留与该版本身份绑定的不可变评审底图，以及尺寸、
方向和源指纹；局部意见同时生成编号标注预览。后续文字编辑可复用未变的图像证据。
Anchor 或编号映射改变时，提交对应的新标注预览。

渲染端接收版本绑定的不可变图像表示，不在存档时重新打开同名路径来“还原”旧图。
捕获过程中源内容变化时，该次提交失败或转为明确待确认状态，不能将新底图标记为旧版本。

证据是评审所需的方向校正预览，不承诺保留原分辨率、全部元数据或完整源媒体。原图／视频
被外部覆盖而没有原始备份时，不能承诺恢复原文件。已有旧协议记录缺少底图时，标注其证据
能力边界；不能从新文件补造旧证据。历史保存已有的可信预览，不为不足的证据造假。

缺少必要证据的旧数据只能保留为明确的历史或待确认项，不能作为完整有效意见发布。
“记录本来没有该证据”与“记录声明的必需证据丢失／损坏”必须区分：前者可表达能力限制，
后者是完整性错误，不能自动降级成普通待确认项来绕过校验。

## 8. Agent 读取契约

### 8.1 三类读取

| 入口 | 结果 | 约束 |
| --- | --- | --- |
| 当前读取 `read-current` | 当前快照的完整有效意见、待确认事项、必要历史引用 | 默认入口，绝不回退历史 |
| 带 `sinceSnapshotId` 的当前读取 | 相同完整结果，附精确增量 | 增量不替代当前清单 |
| 历史读取 `read-history` | 明确指定的存档、旧意见或保存快照 | 标明仅供背景，不是当前执行要求 |

Stream 选择沿用精确 Stream ID 或 task/batch；只有恰好一个 Stream 才能省略。禁止根据目录
顺序、mtime 或最大 ID 猜项目级 latest。人工 Stream 不改写 Production Stream。

结果包含 `projectId`、`reviewStreamId`、`snapshotId`、快照摘要和读取角色。当前部分分为
`actionable` 与 `needsConfirmation`，历史只以 `historyRefs` 引用。除非明确读取历史，不返回
历次全部意见、重复修改过程或旧全文。

同一个目标在一次结果中只能属于有效或待确认的一类；共享文字的不同目标可以分别处于
两类中。尚未建立评审状态的项目返回 `no_review_state`，与已有完整空状态区分。

### 8.2 稳定身份与精确增量

Feedback ID 与 Target ID 是持久身份；画面编号是单张图片、单个快照内的派生显示值。
编辑文字保留 Feedback ID；重绘保留对应 Target ID。不能用“第 3 条意见”跨快照对齐。

增量按身份及内容比较：新增、文字／Anchor／绑定更新、撤回、存档、进入待确认或恢复适用。
同一次更新可以同时包含文字和位置变化，不强行归为一个互斥类别。删除和存档的原因来自
已提交的状态转移记录，不能把“不再出现”一律当成已解决。

默认不输出被撤回内容的旧全文，只给身份、变更原因及必要引用。新增和更新以当前原文为准。
同一条先修改后改回、或新建后删除的中间编辑不强塞给 Agent；必要审计通过显式历史读取。

`sinceSnapshotId` 必须属于本项目、本 Stream 且在已提交可达链中。无起点时不生成假增量；
起点不存在、属其他上下文或超出有界查找范围时，返回完整当前状态并明确
`delta.status = unavailable` 及原因，不偷换起点。用户原文不被语义摘要或自动合并取代。

### 8.3 源检查、完整性与错误

当前读取先固定快照，再核验该快照的结构、摘要、依赖对象、预览编号和素材当前身份。
源核验使用安全打开与流式内容校验，限制并发、支持取消，不把未完成核验视作通过。
缺失、已换版、不可读或无法完成核验的目标放入 `needsConfirmation`，带稳定原因；不得静默丢弃。

快照内保存的是已提交事实；读时新增的检查放在独立的 `sourceChecks`，包含目标、检查时刻
和结果，不改写快照，不另造快照 ID。它可以限制本次可执行范围，但不能代替用户对新素材的
适用性确认。两个快照之间的增量只比较已提交状态；没有新提交的外部文件变化通过当前
`sourceChecks` 表达，不能伪造一条用户编辑事件。

必须区分：

- `ok` 且有效意见为空、待确认为空：当前没有返工意见，不是全部素材验收通过。
- `ok` 且存在待确认项：返回可处理部分与完整待确认列表，不声称所有项均可执行。
- `error`：索引／快照／必需证据损坏、协议不支持、选择有歧义等；不输出成功空清单，
  不自动选择旧快照替代。新索引尚未提交的临时对象不是有效结果。

读取期间新保存不改变已经固定的快照；返回其准确 ID，不承诺“读取结束瞬间仍是最新”。
源文件检查只证明检查时的状态，不消除随后被外部覆盖的竞态。读取说明要求 Agent 在实际
应用修改前核对目标版本；不匹配时停止该项并重新读取，不在同一路径上盲目处理另一份文件。

### 8.4 外部使用边界

读取器不写项目、不启动 Viewer、不联网、不启动 Agent。意见是素材修改数据，不是运行
项目内任意脚本或覆盖其他文件的权限。历史和产出声明也不能扩大用户授权范围。

2026-08-28 批准的实现调整：Node 保留库与 CLI 入口，由独立 Rust 只读程序完成文件访问、
协议校验和投影／增量计算，复用已有 Infrastructure 与 Domain 规则。调用前需要显式本地
构建该程序；读取过程不自动构建、下载、搜索项目内可执行文件或启动桌面应用。
二进制默认来自读取脚本所在可信工作树的 `target/debug/viewer-review-reader`，可通过显式
绝对路径环境变量 `VIEWER_REVIEW_READER` 指定。项目 JSON 不能决定执行路径或命令参数。

内部进程边界使用闭合的一次性 JSON 请求（最多 64 KiB），stdout 为一个结果（最多 64 MiB）；
不新增常驻服务或网络端口。Rust 持有目录句柄，逐级拒绝链接和非规范文件名，源文件逐块摘要。
可变 index 只打开一次：正常原子发布不使已打开的旧索引失效；不可变状态和证据仍核验摘要。
没有评审索引时，只读取现有 `.viewer/project.json` 的项目身份，不创建元数据或虚构 UUID；
没有可验证项目身份的目录返回明确错误，不伪装成合法 `no_review_state`。

协议提供稳定版本与变更原因，便于接收方去重和更新计划，但不承诺跨外部 Agent 的恰好一次
执行。Agent 已经缓存的旧内容和正在运行的工作无法由 Viewer 自动撤销；读取说明明确要求
以本次完整当前清单替换旧的待办理解，而不是不断追加。

## 9. 数据模型与状态所有权

| 对象 | 必须表达的信息 | 所有者／可变性 |
| --- | --- | --- |
| Review Stream | 项目、稳定 Stream 身份、当前快照引用、存档与 legacy 引用 | Viewer；索引原子更新 |
| Review State Snapshot | 快照 ID、前驱引用、完整当前意见／目标状态、素材版本、证据引用、转移原因 | Viewer；提交后不可变 |
| Feedback | 稳定 Feedback ID、文字版本 ID、自然语言原文、可选历史来源 | 通过新快照更新，不原地改历史 |
| Feedback Target | 稳定 Target ID、目标版本 ID、Asset Version、Anchor、适用状态及原因 | 每个目标独立更新或退出当前 |
| Asset Version | 内容身份、源指纹、尺寸／时长、定位信息、可选父版本和关系来源 | 已捕获版本事实不可变 |
| Archive Checkpoint | 存档 ID、依据组、用户选择范围、移出和保留的精确引用、创建时刻 | 不可变；撤销另记事件 |
| Usage Declaration | 声明 ID、项目／Stream、依据快照和摘要、声明覆盖目标、可选产出关联 | Producer 声明；Viewer 核验后留只读副本 |
| Recovery Draft | 未提交文字／几何、预期快照、失败原因 | Viewer 恢复用途，永不被读作指令 |

归档比较单元为 `(feedbackId, textRevisionId, targetId, targetRevisionId)`。文字版本改变会影响
该意见的所有当前目标；某一目标重绘只改变其目标版本。目标显示序号不进入上述身份元组。
新建后立即删除的目标不能复用给另一素材；“继续提出”使用新身份并保留来源引用。

`snapshotId` 使用持久唯一标识；先生成并随提交持久化，重启不重置。UI 命令携带
`expectedSnapshotId`、操作 ID 和载荷摘要。相同操作 ID 的相同载荷重试返回原提交结果；
相同 ID 的不同载荷报冲突。旧请求不能覆盖新状态，重试回执也不能让 UI 回退到旧快照。
操作结果无法确定或有界历史查找耗尽时，明确拒绝重新执行，不能把“无法查明”当作“从未执行”。

每个当前目标必须引用同一项目、同一 Stream 内存在的意见和素材版本；引用无效、身份重复、
目标同时出现于互斥状态等均属于非法状态。归档记录的依据和移出引用也遵守相同的范围校验。

当前状态是完整快照，不要求接收方重放整个事件日志才能使用。前驱和转移记录用于证明
版本关系、解释撤回／存档及恢复；不把逐按键日志设计成第二套事实源。

| 边界 | 职责 | 不承担 |

针对现有 `review_session.rs` 的生命周期复杂度，将持续编辑、存档恢复和只读投影拆为窄用例；

复用已有原子提交、素材安全打开、几何与原生渲染，不顺带重构扫描、搜索、视频播放器或文件事务。

架构规范仍是 Domain ← Application ← Infrastructure／平台适配，桌面组装层注入依赖。
新协议状态通过明确 DTO 传输；通用图片预览不直接导入 Review API。

## 11. 持久化与一致性

### 11.1 v3 布局

Viewer 独占 `.viewer/reviews/`。沿用一个原子索引作为提交入口，新布局为：

```text
.viewer/reviews/
  index.json                         # viewer.review/3，按 Stream 指向当前状态
  write.lock
  states/{snapshotId}.json            # 不可变完整状态及带摘要的前驱引用
  archives/{archiveId}.json           # 存档事实；恢复事件不会改写它
  usage/{declarationId}.json          # 经核验并被用户采用的声明副本
  evidence/{blake3}.png               # 内容寻址的评审底图／标注预览
  recovery/                          # 未提交恢复数据，不是对外指令
  rounds/                            # 保留原 v1/v2 历史位置与字节
  drafts/                            # 保留迁移前 Draft 以便安全恢复
```

索引保留当前快照、存档记录和 legacy 记录的类型、位置、摘要。旧技术版本由当前／存档
引用及带摘要前驱链到达；不枚举目录来猜已提交快照。对象引用图保持无环，存档与结果快照
的相互关系以身份和提交记录表达，不构造互相包含文件摘要的循环。

未变的证据跨技术快照共享；文字修改不重复复制原图。底图和标注图可有不同摘要。每次读取
都核验所需对象与编号映射，不把内容寻址名称本身当成已校验证据。

### 11.2 提交流程

1. 持有写租约，核对当前快照和操作去重记录；验证业务命令和目标范围。
2. 保存必要恢复输入，准备新状态与版本绑定证据。重任务可在租约保护的协调流程中异步执行，
   不长时间阻塞 UI；最终提交前再次比较预期快照。
3. 写入临时对象并核验、持久化，再以不可变最终位置提交。索引此时尚未变化。
4. 存档时同时准备存档记录和移出后的新状态；恢复时同时准备恢复记录和新状态。
5. 原子替换并持久化索引，一次公布全部关联对象，最后返回成功及提交版本。

索引提交前崩溃，旧状态仍是完整有效状态；索引已提交而成功回执丢失，重试返回已提交结果。
遇到提交结果无法确定或索引无法核验时，进入显式恢复，不假装保存失败后另写一次。
不存在“历史没写成功但当前已经清空”或“文本已公开但预览还是旧版”的中间有效状态。

仅保存到恢复 Draft 不等于对外保存成功。保存失败后，已有成功快照仍可按其精确版本读取，
但 UI 必须提示最新编辑尚未提交；读取器无法感知尚未持久化的用户意图，不作相反承诺。

### 11.3 留存与限制

本轮不自动删除已提交技术快照、存档及其证据。原因是只读 Agent 不登记引用租约，Viewer
无法知道外部仍持有哪个版本；不能按“最近没有读取”猜测可删除。通过共享未变证据降低增量
成本，但不承诺存储无限或原媒体可恢复。容量回收是独立设计，不作为本轮隐含清理行为。

继承现有协议资源限制：索引最多 16 MiB，单份状态／存档／声明 JSON 和单个 PNG 最多
64 MiB，单个 PNG 最多 16,777,216 像素，一次快照引用的 PNG 总量最多 4 GiB；
单流当前素材最多 50,000，意见最多 10,000，画笔点单条最多 2,048、
单快照合计最多 200,000。合法 Anchor、文本和 Target 上限继续沿用并由 Schema 与读写器共同校验。

历史链追溯单次最多 10,000 个节点；达到上限时明确返回查找／增量不可用，不猜版本，不影响
能够独立核验的当前完整状态。目录、文件类型、符号链接、路径越界与摘要检查继续严格执行。
空间不足或任何限制命中时保留输入与已提交历史，不能通过自动删除历史或降低校验继续写入。

## 12. 可选返工依据声明

外部声明使用独立 `viewer.review.usage/1`，不能由 Agent 写入 `.viewer/reviews/`。
Producer 可以在项目内自有位置提供声明文件，由用户显式导入；Viewer 不要求固定工具链，
不自动扫描下载目录，不修改既有 `viewer-production.json` 或据此启动生产任务。

声明必须包含：唯一声明 ID、项目 ID、Stream ID、依据 `snapshotId` 与摘要、实际声称使用的
目标身份／版本范围。可选产出映射包含项目内相对路径、内容指纹和对应的旧 Asset Version。
没有产出映射不影响存档依据声明，但不能据此自动建立新旧素材关系。

导入后先做结构、大小、路径、项目、快照及范围核验。有效声明在存档时可预选对应内容；
只有用户采用时才随一次 Viewer 提交保存规范化只读副本。相同声明 ID 和内容去重，ID 相同
而内容不同报冲突。声明中的时间和自由文字不能取代精确版本关系。

核验失败只影响声明和关联建议，不阻止用户按“交接版本未确认”手动存档。声明不包含可执行
命令、脚本加载或自动路径移动能力。文件摘要证明一致性，不证明声明者身份或执行真实性。

## 13. 新旧协议兼容与迁移

当前协议和新模型的语义不兼容，使用明确的 `viewer.review/3`，不在 v2 上静默改变
Completed 或 Draft 的含义。迁移对象是索引与新状态，旧 v1/v2 Completed 和已有证据保持
原位置、原字节、原语义，历史类型标明 `legacy_completed`，不能直接标为 Agent 已使用。

迁移必须在用户首次采用新编辑流程时说明影响，并经写租约、完整核验与原子索引提交：

1. 先核验旧索引、已收录历史和活动 Draft，保存可核验的旧索引备份。
2. 活动 Draft 的有效意见迁入新当前状态；源版本不匹配的进入待确认，不能默认通过。
3. 没有活动 Draft 而存在最新 Completed 时，将其作为“使用情况未确认”的迁移候选，
   允许用户继续评审或仅保留历史。未确认前不重新发布成当前任务，也不判定已返工。
4. 对旧候选编辑或“继续提出”时，按选定意见建立新当前要求并核对素材；未选择的旧意见
   不跟随激活。历史只读不再禁用当前工作台的新增工具。
5. 提交 v3 索引和完整新状态后才报告迁移成功；失败维持可核验的旧入口或明确恢复状态。

新当前读取器只按 v3 当前语义工作；遇未迁移旧索引返回 `migration_required`。旧
`read-latest.mjs` 保留 legacy 读取职责，但遇 v3 明确报不支持并指向新入口，不转而寻找
最近存档。历史读取入口按记录自身版本分派，可继续查看旧数据。

旧软件不能写入不支持的索引主版本；禁止降级、新增一个继续指向旧 Completed 的“兼容
latest”或把新历史复制成旧可执行结果。已保存于外部的旧副本无法被 Viewer 撤销，需在
迁移提示与读取说明中说明。

本文整体审阅通过后，实施计划须安排新的持久化／读取 ADR 及 Schema 契约测试。只有实际
落地并验证后，才更新产品规格、指南、隐私说明和当前协议文档；不能提前把计划写成现有功能。
现有设计中与本方案冲突的固定名单、完成锁定和默认通过规则，在实施时明确标为被替代，
其余图片工作台、几何和安全边界继续有效。

## 14. 验收标准

以下均为未来实施的验收要求，不是本次文档编写已完成的功能测试。

| 场景 | 必须结果 |
| --- | --- |
| 首次保存、完成状态后新增、打开另一张图片 | 无强制完成门槛；成功保存可读，新增素材按意见加入 |
| 连续编辑／重绘同一条意见 | 身份稳定、旧内容被替代、编号与预览属于同一快照 |
| Agent 读 B、用户写 C 后存档 B | 历史为 B，C 后补内容保留，不复活已删除项 |
| 没有回传，用户记不清依据 | 允许确认范围后手动存档，明确未知，不猜版本 |
| 只返回图 1，图 2 未返回 | 图 2 保留；共同文字的图 1 目标可独立存档 |
| 部分目标重绘、共同文字编辑 | 精确比较对应目标／文字版本，不错误清除其他目标 |
| 同路径覆写、保持 mtime 的内容变化 | 旧目标不可直接作用到新文件；保存旧证据不读取新图冒充 |
| 改名／移动、重复内容、多候选、缺失文件 | 位置与业务关系分离；歧义明确，不自动绑定或通过 |
| 旧问题仍在并“继续提出” | 新当前身份、历史来源、位置适用性确认，原文可复用 |
| 存档后撤销、已有新意见再恢复 | 追加恢复事实，不覆盖新内容；素材变化仍需确认 |
| 新增→修改→删除或改回原文 | 当前结果准确，增量不重放无效中间要求 |
| 删除已被 Agent 读到的“改蓝色” | 表示撤回，不生成“改回原色”的新指令 |
| 当前空、仅待确认、结构损坏 | 三种结果明确区分；不回退历史、不静默漏项 |
| 无 since、未知 since、其他项目／Stream 的 since | 当前完整结果可独立使用，增量不可用时说明原因 |
| 保存／渲染／索引提交各阶段中断 | 无混合版本、无意见丢失、无虚假成功，重试可判定 |
| 重复点击、回执丢失、乱序或过期命令 | 幂等且有版本守卫，不重复存档，不覆盖后续状态 |
| 两进程写入、只读目录、磁盘满、资源超限 | 写入受控，保留已提交状态和用户输入，不降低安全校验 |
| 读取期间继续保存或源文件再变化 | 固定快照身份正确，核验边界说明准确，不承诺实时执行锁 |
| 同一快照两次读取之间源文件变化 | 仅读时检查和可执行范围变化，不改快照、不伪造增量 |
| 旧数据原本无证据、已声明证据实际损坏 | 能力限制与完整性错误分开；后者不能被静默降级 |
| 声明伪造范围、错项目、重复 ID 冲突、路径穿越 | 拒绝声明或关联，不执行内容，手动未知存档仍可用 |
| v1/v2 迁移、旧读取器读 v3、未知未来主版本 | 旧字节不变，语义不混用，不降级，不泄漏旧任务为当前 |
| 多快照共享证据、旧版本被显式引用 | 引用完整、不可变，无后台清理导致悬空引用 |
| 原生图片四处标注、缩放／旋转／导航／重启 | 当前与历史标记定位正确，已有原生轮廓修复不回归 |

验证分层：Domain 状态与差集性质测试，Repository 故障注入与迁移测试，Schema／独立读取器
契约测试，UI 协调与输入保留测试，最后使用隔离测试工程做真实图片多轮评审与原生回归。
继续检查视频浏览、搜索、文件操作和预览导航，避免跨层改动破坏既有能力。

真实测试使用 `下载/测试图` 的受控副本或项目现有临时验收副本，不修改用户原始素材，不把
仓库只读 fixture 当作可写工程。实施门禁沿用 `pnpm verify:clean` 及涉及边界的专项门禁，
没有签名、公证、正式安装包或发售验收。

## 16. 设计依据与相关资料

### 16.1 官方产品资料

以下来自本轮已完成的官方文档调研，作为设计机制参考，而非承诺完整复刻这些产品。

- [Filestage：文件版本](https://help.filestage.io/en/articles/2211321-manage-different-versions-of-a-file)：
  新版本与旧意见分离，历史可追溯；Viewer 不照搬基于文件名的自动业务匹配。
- [Filestage：跨版本复制意见](https://help.filestage.io/en/articles/6318439-copy-comments-between-reviewer-groups-and-versions)：
  显式带入历史意见；Viewer 增加来源关联与新素材适用性核对。
- [Figma：Dev Mode 状态与变更](https://help.figma.com/hc/en-us/articles/26781702258583-Dev-Mode-statuses-and-notifications)：
  交接状态与继续编辑可以并存；Viewer 依据精确快照解释后补变化，不照搬审批流程。
- [Figma：版本历史](https://help.figma.com/hc/en-us/articles/360038006754-View-a-file-s-version-history)：
  后台保存与用户命名里程碑分离；Viewer 的存档频率不等于保存频率。
- [GitHub：评审 API](https://docs.github.com/en/rest/pulls/reviews)：
  评审关联具体提交版本；Viewer 借鉴精确依据，不把版本关联当作执行证明。
- [Dropbox Replay：反馈](https://help.dropbox.com/view-edit/dropbox-replay-feedback)：
  版本与意见处理状态分别表达；Viewer 的归档、撤回和适用性不能折叠成“完成”。
- [Frame.io：版本堆栈](https://help.frame.io/en/articles/9101068-version-stacking)：
  默认当前与按需历史并存；Viewer 保持当前读取与历史读取的角色边界。
